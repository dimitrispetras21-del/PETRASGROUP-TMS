# DECISION LOG

Γιατί κάναμε ό,τι κάναμε. Όχι τι — αυτό το λέει το `git log`.

## Κανόνας

Μία εγγραφή ανά **απόφαση**, όχι ανά commit. Απόφαση = κάτι που θα μπορούσε
εύλογα να είχε γίνει αλλιώς. Μορφή:

```
### YYYY-MM-DD · <περιοχή> · <η απόφαση σε μία γραμμή>
**Επιλογή:** τι διαλέξαμε
**Εναλλακτικές:** τι απορρίφθηκε και γιατί
**Απόδειξη:** τι το στηρίζει (αρχείο:γραμμή, νούμερο, δοκιμή)
**Ποιος:** owner / Claude / και οι δύο
```

Αν κάτι ανατραπεί αργότερα **δεν σβήνεται** — μπαίνει νέα εγγραφή που δείχνει
πίσω. Η αλλαγή γνώμης είναι πληροφορία.

## 2026-08-10 · Τι πήγε στραβά

### Η ενοποίηση της φόρμας αναιρέθηκε
Το `be2fa5b` ένωσε το groupage μέσα στη φόρμα εθνικών. Έσπασαν **τρία**
πράγματα μαζί — αναζήτηση, συμπλήρωση, επεξεργασία. Revert: `68ecbf4`.

**Το ελάττωμα:** σε επεξεργασία groupage παραγγελίας το κουμπί δρομολογούνταν
στον writer **δημιουργίας** — κάθε αποθήκευση θα έφτιαχνε διπλότυπα σε
τέσσερις πίνακες.

**Η αιτία, βαθύτερα:** στάλθηκε σε παραγωγή αλλαγή στη δημιουργία παραγγελιών
**χωρίς να ανοίξει η φόρμα ούτε μία φορά**. Επαναλήφθηκε και στη φόρμα
groupage, όπου ο owner βρήκε τρία προβλήματα με μία δοκιμή.

**Κανόνας που προκύπτει:** ό,τι αφορά δημιουργία παραγγελιών δεν φεύγει
αδοκίμαστο. Δεκαεπτά commits σε μία μέρα χωρίς οπτικό έλεγχο ήταν το
πραγματικό ρίσκο, όχι η πολυπλοκότητα του κώδικα.

## Ανοιχτό — προτεινόμενη αναθεώρηση αρχιτεκτονικής

Ο owner πρότεινε (10/08): οι παραγγελίες να καταχωρούνται **μία-μία και
ξεχωριστά**, και η σύνθεση φορτίου να είναι **χωριστή πράξη** που παράγει το
CONSOLIDATED LOAD και από εκεί το NAT_LOAD.

**Γιατί είναι σωστό:** πώληση και σύνθεση φορτίου είναι δύο αποφάσεις σε
διαφορετικές στιγμές, με διαφορετική πληροφορία. Το να τις παίρνει και τις δύο
η φόρμα είναι σωστό μόνο στην ΚΑΘΟΔΟ, ποτέ στην ΑΝΟΔΟ — όπου το ποιο φορτηγό
παίρνει ποια σημεία αποφασίζεται όταν βλέπεις τον όγκο της εβδομάδας.

**Συνέπεια:** η φόρμα δεν χρειαζόταν ποτέ να αλλάξει.

**Προς έλεγχο πριν αποφασιστεί:** αν κάθε παραγγελία παράγει γραμμές, η ουρά
του Pick Ups γεμίζει με τα πάντα. Πιθανή απάντηση: αυτόματη σύνθεση για τα
μονά, ουρά μόνο για όσα θέλουν απόφαση. Θέλει δοκιμή σε πραγματικό χειμωνιάτικο
όγκο.

**Κατάσταση:** ΔΕΝ αποφασίστηκε. Δεν γράφτηκε στο SPEC.

## 2026-08-12 — GRP trip: σειρά παράδοσης μέσα στο Group ID
**Επιλογή**: Η σειρά παράδοσης των ομάδων (Pair/groupage) αποθηκεύεται ως suffix στο υπάρχον πεδίο ORDERS `Group ID`: `GRP-xxx|recA,recB,recC` (ίδια τιμή σε όλα τα μέλη).
**Εναλλακτικές**: (α) νέα στήλη `group_seq` — απορρίφθηκε: θέλει SQL + view trick + worker deploy για ένα integer· (β) ξεχωριστός πίνακας groups — υπερβολή για UI-level ομαδοποίηση που δεν αγγίζει τιμολόγηση.
**Απόδειξη**: το collapse βασίζεται σε ισότητα string του Group ID, άρα το κοινό suffix δεν το σπάει (verified live W33). Fallback χωρίς suffix: ταξινόμηση κατά Delivery DateTime.
**Παγίδα**: κάθε εμφάνιση του Group ID σε UI θέλει `.split('|')[0]`. Το `_wiMerge` γράφει σκέτο gid → η σειρά επανέρχεται στην default μέχρι νέο save.
**Ποιος**: owner (εγκεκριμένο πρωτότυπο grp_trip_proto, 12/8).

## 2026-08-12 — Παλέτες: τα ονόματα έρχονται embedded, όχι από τα lookups
**Επιλογή**: Το `GET /pallets/movements` γυρίζει `select=*,clients(company_name),partners(company_name),locations(name)` (PostgREST embedding). Οι `_plvName/_plvLoc` διαβάζουν πρώτα το embedded όνομα και πέφτουν στα `/pallets/lookups` μόνο ως fallback.
**Εναλλακτικές**: (α) ανέβασμα του limit στα lookups (500→5000, commit 43f7652) — δεν αρκεί: η PostgREST κόβει στα 1000 από `db-max-rows`, όριο του server, όχι του query· (β) δεύτερο round-trip ανά σελίδα για ανάλυση ονομάτων — περιττό, το join το κάνει η βάση δωρεάν.
**Απόδειξη**: live GET στη Supabase γύρισε 200 με `clients:{company_name}` / `locations:{name}` και `partners:null` σε κίνηση CLIENT. Μονή FK ανά πίνακα (003_pallets_schema) → κανένα ambiguous embed. Deployed worker version 5c72d2f5.
**Παγίδα**: τα lookups εξακολουθούν να τροφοδοτούν τα dropdown της «Νέα κίνηση» — εκεί το όριο των 1000 ΠΑΡΑΜΕΝΕΙ ανοιχτό (πελάτες μετά το όριο δεν επιλέγονται). Θέλει φίλτρο `active=true` ή typeahead· δεν αποφασίστηκε.
**Ποιος**: owner (αναφορά «Πελάτης #1314» στο ημερολόγιο, 12/8).
