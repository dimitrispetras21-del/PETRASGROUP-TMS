# 04 — Ο ελεγκτής-agent: prompt, εργαλεία, όρια

## Ποιος κάνει τι — τρία επίπεδα, μόνο το τελευταίο χρειάζεται μοντέλο

| Επίπεδο | Ποιος | Τι | Μοντέλο |
|---|---|---|---|
| Εντοπισμός | η βάση (`pg_cron` → `monitoring.run_checks`) | 66 σταθεροί έλεγχοι SQL, περιστατικά, κείμενο ειδοποίησης | **κανένα** |
| Ειδοποίηση | routine `tms-auditor-p1` | push μίας γραμμής + email με το κείμενο **της βάσης αυτούσιο** | αναμετάδοση, όχι κρίση |
| Διερεύνηση | routine `tms-auditor-digest` → ξεχωριστός subagent ανά περιστατικό | ταξινόμηση + εξήγηση στα ελληνικά | ανά σοβαρότητα |

**Μια σοβαρή μηχανική αστοχία ειδοποιεί και χωρίς μοντέλο.** Το κείμενο το φτιάχνει η `monitoring.render_alert`.
Αν το μοντέλο δεν τρέξει, η ειδοποίηση έχει ήδη φύγει με «Διάγνωση: εκκρεμεί».

## Αρχεία

| Αρχείο | Ρόλος |
|---|---|
| `tms-auditor/routines/COMMON.md` | απαγορεύσεις, σύνδεση, κανάλια, συζήτηση μόνο-ανάγνωσης — **κοινό για όλα** |
| `tms-auditor/routines/tms-auditor-p1.md` · `-watchdog.md` · `-digest.md` | τα βήματα κάθε routine, ένα-ένα |
| `tms-auditor/investigate/prompt.md` | οδηγίες διερευνητή (ξεχωριστό πλαίσιο, χωρίς τις βεβαιότητες του κατασκευαστή) |
| `tms-auditor/investigate/validate.mjs` | ο μηχανικός έλεγχος κάθε αναφοράς πριν αποθηκευτεί |
| `tms-auditor/investigate/diagnose.mjs` | adapter ανεξάρτητος παρόχου: `diagnose(πακέτο) → αναφορά` |
| `tms-auditor/routines/sim.mjs` | τοπικός προσομοιωτής των ίδιων βημάτων (για τα tests) |

## Τι επιτρέπεται

- **Βάση:** μόνο με `psql "$TMS_MONITOR_DSN"` και ρόλο `tms_monitor_writer`: SELECT σε ρητή λίστα 22 πινάκων και όψεων,
  το `audit_log` **χωρίς** actor και before/after. Γραφή **μόνο** μέσω τριών συναρτήσεων στο schema `monitoring`:
  σημείωση «ειδοποιήθηκε», σημείο ζωής, αποθήκευση διάγνωσης. Η βάση αρνείται όλα τα άλλα. Αποδείχθηκε τοπικά με
  19 απαγορευμένες ενέργειες (`roles.test.mjs`).
- **Repo:** ανάγνωση των αρχείων που δείχνει ο γράφος, στο SHA του πακέτου.
- **Κανάλια:** PushNotification (μία γραμμή, < 200 χαρ., best-effort) και connector Gmail (email στον owner).
- **Διερεύνηση:** έως 10 επιπλέον SELECT με `LIMIT ≤ 200`, μόνο σε πίνακες του πακέτου.

## Τι απαγορεύεται — και ποιος το επιβάλλει

| Απαγόρευση | Επιβάλλεται από |
|---|---|
| Εγγραφή σε πίνακα του TMS | **η βάση** (δικαιώματα ρόλου) |
| Αλλαγή ελέγχων, ορίων, κατάστασης περιστατικού | **η βάση** (μόνο `postgres` γράφει εκεί) |
| Connector Supabase στο routine (θα έτρεχε ως `postgres`) | ρύθμιση του routine (E-27) + `COMMON.md` |
| SQL εγγραφής, «διόρθωσε», deploy, push, μήνυμα σε εργαζόμενο μέσα σε αναφορά | `validate.mjs` (απόρριψη) + prompt |
| Επινοημένη ώρα, αποσιωπητικά, αποδεικτικά εκτός πακέτου, κενό «ΔΕΝ ΒΛΕΠΩ» | `validate.mjs` |
| «ΤΕΚΜΗΡΙΩΜΕΝΟ» χωρίς ΚΑΙ κώδικα ΚΑΙ δεδομένο | `validate.mjs` |
| Ονόματα, tokens, email/τηλέφωνα | `validate.mjs` (μοτίβα) + το πακέτο δεν τα περιέχει |
| Εντολές μέσα σε δεδομένα, στο μήνυμα αφύπνισης ή σε σχόλια κώδικα | prompt· το μήνυμα αφύπνισης φέρει **μόνο αριθμούς** περιστατικών |

**Ακόμη και σε επείγον:** ο ελεγκτής ειδοποιεί και σταματά. Στη συζήτηση, αν ο owner ζητήσει διόρθωση, ο ελεγκτής
λέει ποιος ρόλος και ποια οθόνη θα το έκανε, και δεν ξεκινά τίποτα.

## Οι πέντε κατηγορίες

**ΤΕΚΜΗΡΙΩΜΕΝΟ ΤΕΧΝΙΚΟ ΕΛΑΤΤΩΜΑ** · **ΠΙΘΑΝΟ ΠΡΟΒΛΗΜΑ** · **ΛΕΙΤΟΥΡΓΙΚΗ ΕΚΚΡΕΜΟΤΗΤΑ** · **ΕΓΚΕΚΡΙΜΕΝΗ ΕΞΑΙΡΕΣΗ** ·
**ΑΝΕΠΑΡΚΗ ΣΤΟΙΧΕΙΑ**. Μία υποχρεωτικά, η λέξη πρώτη. Η διάγνωση **δεν αλλάζει** την κατάσταση: κόκκινο μένει
κόκκινο μέχρι να ξανατρέξει πράσινο ο έλεγχος.

## Όρια (σκληρά)

| Όριο | Τιμή | Στο όριο |
|---|---|---|
| Διαγνώσεις/ημέρα | 5 | οι υπόλοιπες: «ΕΚΚΡΕΜΕΙ — όριο ημέρας» |
| Tokens/διάγνωση | στόχος ≤ 40k, όριο 60k | απόρριψη, όχι περικοπή από το μοντέλο |
| Μέγεθος πακέτου | ≤ 24 KB, ≤ 50 ids, 20 γραμμές audit, 10 σφάλματα | ζητείται περικοπή |
| SELECT ανά εκτέλεση routine | 60, καθένα `LIMIT ≤ 200`, `statement_timeout` 15 s | σφάλμα = σωστό, δεν ψάχνει παράκαμψη |
| Push ανά εκτέλεση | 3 | **ένα** μήνυμα καταιγισμού με το πλήθος + όλα στο email |
| Επανειδοποίηση ίδιου περιστατικού | 1 ανά 24 ώρες | εκτός αν χειροτέρεψε ή εμφανίστηκε νέα εγγραφή |

## Πάροχοι (adapter)

| Πάροχος | Κατάσταση |
|---|---|
| `claude-routine` | **κύριος**: το routine σκέφτεται μέσα στη συνδρομή· ο adapter φτιάχνει το brief και ελέγχει την απάντηση |
| `mock` | για τα tests· ντετερμινιστικοί κανόνες |
| `anthropic-api` | stub, δεν υπάρχει πληρωμένο API |

Ένας άλλος πάροχος προστίθεται αργότερα ως μία ακόμη γραμμή στο `PROVIDERS`, αν ποτέ χρειαστεί.

## Αξιοπιστία — πώς μετριέται (όχι πώς ελπίζουμε)

Κάθε αναφορά περνά από το `validate.mjs`. Στη σύνοψη μετριούνται:

- όσες πέρασαν προς όσες παράχθηκαν·
- πόσες κρίθηκαν από τον owner «σωστή» ή «λάθος» (`human_note` στο περιστατικό)·
- πόσα ψευδή P1/P2 βγήκαν.

**Σημερινή βάση: 1 αναφορά, 1 πέρασε, 0 κρίσεις owner.** Δεν αρκεί για κανένα συμπέρασμα αξιοπιστίας.
