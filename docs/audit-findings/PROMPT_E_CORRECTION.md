# ΔΙΟΡΘΩΣΗ πριν την εκτέλεση του Ε — μία ερώτηση `CASE` ως μοναδική πηγή

> Παραλήπτης: **Claude Code / Fable 5**. 25/8/2026.
> Η **λογική** της λίστας εγκρίνεται. Τα **counts** όχι — μη τρέξεις ακόμη.

## Τι δεν κλείνει

Το σύνολο σου είναι σωστό: **567 με τιμή + 594 κενές = 1.161** ✓ — το
επαλήθευσα ανεξάρτητα. Η **κατανομή** όμως αποκλίνει:

| Κανόνας | Δήλωσες | Μετρήθηκε στη βάση |
|---|---|---|
| 1 · `NOTES :` | 4 | **4** ✓ |
| 2 · CLIENT (κάθε γραφή) | 506 | **493** |
| 3 · λεξιλόγιο | 16 | **26** |
| 4 · ελεύθερο κείμενο | 36 | **40** |
| 5 · ψηφία | 4 | **4** ✓ |

Και υπάρχει εσωτερική αντίφαση στη λίστα σου: ο **πίνακας** του Κανόνα 3
αθροίζει 28 (11+4+2+7+2+1+1) ενώ το **κείμενο** λέει 16. Μετά τις δύο
μετακινήσεις που περιγράφεις, τα νούμερά σου δίνουν 566, όχι 567.

## Γιατί δεν το προσπερνάμε

Δεν είναι αριθμητική υγιεινή. Οι κανόνες στέλνουν σε **διαφορετικές στήλες**:
ο 2 αδειάζει το `type`, ο 3 κρατά καθαρό τύπο. Η διαφορά 16↔26 σημαίνει ότι
**δέκα εγγραφές διαφωνούν για τον προορισμό τους**. Αν δέκα συνεργεία και
πρατήρια περάσουν ως «πελάτες», το `type` τους αδειάζει και **παύουν να είναι
συνεργεία** — το φίλτρο δεν τα βρίσκει, η κάρτα λέει «χωρίς τύπο».

Αναστρέψιμο μέσω `type_raw`, ναι. Αλλά μόνο αν το προσέξει κάποιος.

## ⛔ Ο κανόνας που δεν παραβιάζεται

Αν η συναλλαγή σκάσει λέγοντας «περίμενα Χ, βρήκα Υ»:
**ΣΤΑΜΑΤΑΣ ΚΑΙ ΤΟ ΑΝΑΦΕΡΕΙΣ. ΔΕΝ αλλάζεις το αναμενόμενο για να περάσει.**

Ένα δίχτυ που το προσαρμόζεις για να περάσει δεν είναι δίχτυ — γίνεται σφραγίδα,
και την επόμενη φορά που θα υπάρχει πραγματικό πρόβλημα θα περάσει σιωπηλά.
Είναι το μοτίβο που παρήγαγε τα μισά ευρήματα του audit.

## Η διόρθωση: μία `CASE`, δύο χρήσεις

Μη γράφεις τα αναμενόμενα με το χέρι δίπλα στη λίστα. **Μία ερώτηση κατατάσσει
και τις 1.161 και βγάζει τα σύνολα** — και η **ίδια** τρέχει ως έλεγχος μέσα
στη συναλλαγή. Έτσι ταξινόμηση και αναμενόμενο **δεν μπορούν** να διαφωνήσουν,
γιατί είναι το ίδιο πράγμα (**αρχή 3**).

Αυτή έτρεξα εγώ — συμφώνησε μαζί της ή διόρθωσέ την, αλλά **μία** να μείνει:

```sql
WITH v AS (
  SELECT id, type, lower(btrim(type)) AS t
  FROM locations WHERE deleted_at IS NULL
), c AS (
  SELECT id, type,
    CASE
      WHEN type IS NULL OR btrim(type)='' THEN '0 · κενό'
      WHEN t LIKE 'notes :%'              THEN '1 · NOTES:'
      WHEN type ~ '[0-9]{3,}'             THEN '5 · ψηφία (χειροκίνητα)'
      WHEN t IN ('client depot','fuel station','partner warehouse','partner',
                 'veroia hub','custom point','client : custom point','συνεργειο',
                 'service','πλυντηριο','scania bulgaria','volvo sofia',
                 'ανεφοδιασμος καυσιμων, συνεργαζομενο πρατηριο')
           OR t LIKE 'συνεργειο%' OR t LIKE 'ηλεκτρολόγος%'
                                          THEN '3 · λεξιλόγιο'
      WHEN type ~* 'cl[ie]*n[et]*\s*[:;]' THEN '2 · CLIENT'
      ELSE                                     '4 · ελεύθερο κείμενο'
    END AS κανόνας
  FROM v
)
SELECT κανόνας, count(*) AS εγγραφές, count(DISTINCT type) AS διακριτές
FROM c GROUP BY κανόνας ORDER BY κανόνας;
```

Σειρά της `CASE` = σειρά προτεραιότητας: κενό → NOTES → ψηφία → λεξιλόγιο →
CLIENT → ελεύθερο. Το ελεύθερο είναι **catch-all**, γι' αυτό τελευταίο.

Αποτέλεσμα αναφοράς (δικό μου, στα 1.161 ενεργά):
**594 · 4 · 493 · 26 · 40 · 4** — άθροισμα με τιμή **567**, γενικό **1.161**.

## Τι θέλω πριν τρέξει οτιδήποτε

1. Τρέξε την `CASE`. Αν διαφωνείς με κάποια γραμμή της, πες **ποια τιμή** και
   **γιατί** — η διαφωνία στη λογική είναι θεμιτή, η διαφωνία στα νούμερα όχι.
2. **Δώσε τη λίστα των εγγραφών του Κανόνα 3** (26) ονομαστικά. Εκεί είναι η
   απόκλιση των δέκα — θέλω να δω ποιες είναι, όχι πόσες.
3. Τα αναμενόμενα κάθε `UPDATE` **παράγονται από αυτή την `CASE`**, όχι
   γραμμένα με το χέρι.
4. Μετά την εκτέλεση, ξανατρέξε την **ίδια** ερώτηση: πρέπει να δίνει
   `0 · κενό` = 594 + 4 + 493 + 40 = **1.131**, `3 · λεξιλόγιο` = **26**,
   τίποτα άλλο. Αυτό είναι το τελικό assertion.

Τα υπόλοιπα του Ε (Worker, φόρμα, «ΑΝΑ ΚΙΝΗΣΗ» στην ίδια παράδοση) μένουν
ακριβώς όπως εγκρίθηκαν.
