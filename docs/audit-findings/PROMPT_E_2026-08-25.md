# ΕΝΤΟΛΗ — Βήμα Ε: καθαρισμός `type` + αντικατάσταση «ΑΝΑ ΚΑΤΗΓΟΡΙΑ»

> Παραλήπτης: **Claude Code / Fable 5**. Εγκρίθηκε από owner 25/8/2026.
> Προϋπόθεση: Α/Β/Γ/Δ είναι ήδη live (`fb77419`, `c8b4837`).

## Η έγκριση και το όριό της

Ο owner εγκρίνει τη migration **μαζί με** την αντικατάσταση του πίνακα
«ΑΝΑ ΚΑΤΗΓΟΡΙΑ». Τα δύο **φεύγουν στην ίδια παράδοση** — όχι σε δύο.

**Καμία εκτέλεση SQL πριν εγκριθεί η λίστα αντιστοίχισης 1-προς-1.**

## ⚠️ Πρώτα: ξαναβγάλε τα νούμερα

Η λίστα (~210 τιμές, ~490 εγγραφές `CLIENT :`) παρήχθη **πριν** εκτελεστεί το Δ.
Οι ενεργές τοποθεσίες είναι πλέον **1.161**, όχι 1.185. Ξαναμέτρησε κάθε κανόνα
με `deleted_at IS NULL` και δώσε τα ενημερωμένα counts — αλλιώς τα «αναμενόμενα
αποτελέσματα» δεν θα ταιριάξουν και ο έλεγχος θα φωνάξει ψευδώς.

## Α. Migration

Σειρά, χωρίς παρέκκλιση:

1. **`type_raw text` ΠΡΩΤΟ**, με πλήρες αντίγραφο του `type` για **όλες** τις
   εγγραφές (και τις διαγραμμένες). Αναστροφή όλου του βήματος:
   `UPDATE locations SET type = type_raw`. Χωρίς αυτό δεν προχωράει τίποτα.
2. `notes text` · `tags text[]` · `phone text`.

Σε συναλλαγή, με counts πριν/μετά ανά statement, **μετά τις 15:00**.

## Β. Οι κανόνες αντιστοίχισης

| # | Κανόνας | Προορισμός |
|---|---|---|
| 1 | `NOTES : *` | → `notes` αυτούσιο· `type` αδειάζει |
| 2 | Κάθε `CLIENT / CLINET / Client : *` (όλες οι γραφές) | `type` αδειάζει· ιστορικό μένει στο `type_raw` |
| 3 | Δομημένο λεξιλόγιο | → κανονικοποιημένο `type` (~7 τιμές) |
| 4 | Ελεύθερο κείμενο / σκέτα ονόματα | → `notes` αυτούσιο |
| 5 | Οι 4 με ψηφία | **χειροκίνητα**: τηλέφωνο ΡΟΚΑΚΗ → `phone`· 3 διευθύνσεις → `address`/`notes` |
| 6 | `ΤΣΑΚΙΡΗΣ` = `ΤΣΙΑΚΙΡΗΣ` | σωστή γραφή **ΤΣΙΑΚΙΡΗΣ** — στη λίστα ενοποιήσεων του παράγωγου |

Το λεξιλόγιο του κανόνα 3: `Client Depot` · `Fuel Station` (+«ΑΝΕΦΟΔΙΑΣΜΟΣ…») ·
`Partner Warehouse` (+σκέτο «PARTNER») · `ΣΥΝΕΡΓΕΙΟ` (4 γραφές + SCANIA
BULGARIA / VOLVO SOFIA / «Ηλεκτρολόγος…», με το περίσσευμα σε `notes`) ·
`Custom Point` · `Veroia Hub` · `Πλυντήριο`.

**Ο πελάτης ΔΕΝ γίνεται tag.** Παράγεται από τις παραγγελίες:
`COALESCE(order_stops.client_at_stop_id, orders.client_id, national_orders.client_id)`
— 267/267 καλυμμένες. Χειροκίνητο tag πελάτη = τρίτη λίστα που αποκλίνει
(**αρχή 3**). Το `tags` είναι **μόνο** για ό,τι δεν ξέρουν τα δεδομένα
(«χωρίς κλαρκ», «τηλεφώνησε πριν»).

## Γ. Η αντικατάσταση — στην ΙΔΙΑ παράδοση

Μετά τον κανόνα 2, ~95% των τοποθεσιών θα είναι «χωρίς τύπο» και ο πίνακας
**«ΑΝΑ ΚΑΤΗΓΟΡΙΑ» θα πέσει από 48 σε ~7 κατηγορίες**. Αυτό είναι η αλήθεια — οι
48 δεν ήταν ποτέ κατηγορίες, ήταν ονόματα πελατών σε λάθος πεδίο. Αλλά **δεν
επιτρέπεται να μείνει ούτε μία μέρα άδειος πίνακας**.

Στην Επισκόπηση, **αντικατάστησε** το «ΑΝΑ ΚΑΤΗΓΟΡΙΑ» με **«ΑΝΑ ΚΙΝΗΣΗ»**:
ΕΞΑΓΩΓΗ · ΕΙΣΑΓΩΓΗ · ΚΑΘΟΔΟΣ · ΑΝΟΔΟΣ, με τον **ίδιο δείκτη** που τροφοδοτεί
ήδη το φίλτρο (μετρήσεις **τοποθεσιών**, όχι παραγγελιών — 110 με τύπο σήμερα).
Ίδιο ύφος μπάρας, καμία νέα γραφιστική γλώσσα.

Οι τοποθεσίες χωρίς καμία κίνηση λένε ρητά «καμία κίνηση καταγεγραμμένη» — ποτέ
σιωπηλό κενό (**αρχή 1**).

## Δ. Worker

Τα νέα labels `Notes` / `Tags` / `Phone` θέλουν γραμμές στον χάρτη **LOCATIONS**
— αλλιώς σιωπηλή απόρριψη με 200 OK. Μπαίνουν στην **ίδια δέσμη deploy** με το
ήδη γραμμένο `"Order ID": "id"` και τα εκκρεμή του `/costs`. Ισχύει ο φρουρός
των τριών, και deploy **μόνο μετά τις 15:00**.

## Ε. Απόδειξη πριν πεις «έτοιμο»

1. Counts ανά κανόνα, **πριν και μετά**, από τη βάση — όχι από την οθόνη.
2. `type_raw` γεμάτο για **όλες** τις εγγραφές πριν αγγιχτεί το `type`.
3. Η φόρμα γράφει `Notes`/`Phone` και **η τιμή διαβάζεται πίσω** μετά από
   reload — το μάθημα του read-drop: η εγγραφή δεν αποδεικνύεται από το toast.
4. «ΑΝΑ ΚΙΝΗΣΗ» ζωντανό στην ίδια παράδοση με τη migration.
5. Γραμμένη η αναστροφή στο commit και στο session log.
