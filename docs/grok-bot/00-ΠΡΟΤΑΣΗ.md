# Τεχνικός ελεγκτής του TMS — πρόταση προς τον owner

Ημερομηνία: **22/9/2026** · Session «Grok Bot ελεγκτής» · **Μόνο ανάγνωση: τίποτα δεν άλλαξε, τίποτα δεν ενεργοποιήθηκε, τίποτα δεν αγοράστηκε.** Όλα τα αρχεία αυτού του φακέλου είναι πρόταση. Αναλυτικά: `01` κατάσταση, `02` σταθεροί έλεγχοι, `03` σύνδεση/δικαιώματα, `04` πιλότος, `05` εναλλακτικές, `skill-*` τα δύο εγχειρίδια.

## 1. Τι υπάρχει και επιβεβαιώθηκε σήμερα

Μέθοδοι: ανάγνωση κώδικα, `SELECT` στη βάση, ερωτήματα στα logs του Cloudflare (μόνο ανάγνωση), `GET` στη δημόσια εφαρμογή. Καμία σελίδα με λογαριασμό, κανένα test.

- **Ένα περιβάλλον, η παραγωγή.** Δεν υπάρχει δοκιμαστικό. Η εφαρμογή στο GitHub Pages είναι ακριβώς το `main` (επιβεβαιώθηκε 22/9). Ο Worker «staging» **είναι** η παραγωγή.
- **Η βάση είναι μικρή** (όλη < 20 MB, χωρά στη μνήμη)· η υγεία των ελέγχων είναι **εν μέρει άγνωστη** (βλ. σιωπή `app_errors` παρακάτω). Οι 9 όψεις ελέγχου που ήδη υπάρχουν δίνουν σήμερα: μισθοδοσία χωρίς κενά (0), VS όλα με cross-dock (42/42), 0 ορφανά φορτία, ράμπα νέα 16/16 δεμένες, DKV έγγραφα = άθροισμα γραμμών (0 διαφορές). **Ένα κόκκινο:** 27 παραδομένες παραγγελίες χωρίς τιμή (ουρά dispatcher, όχι λάθος κώδικα — η λογίστρια δεν μπορεί να τις τιμολογήσει).
- **Καταγραφές:** ο Worker κρατά κάθε αίτημα στο Cloudflare για 7 ημέρες (50.361 την εβδομάδα, 2 σφάλματα server, 71 ληγμένα tokens). Το `audit_log` γράφει κάθε επιτυχή αλλαγή (6.337 μέχρι σήμερα). Το `app_errors` γράφει σφάλματα browser — **αλλά σιωπά από 17/9**, και δεν ξέρουμε αν είναι υγεία ή βλάβη.
- **Ρόλοι:** 5 ρόλοι, 18 λογαριασμοί, 7 ενεργοί. **Κανένας ρόλος μόνο-ανάγνωσης**, ούτε στο TMS ούτε στη βάση.
- **Έλεγχοι:** υπάρχουν 17 critics, Worker tests, 1 CI check, 9 όψεις — **κανένας δεν τρέχει χωρίς άνθρωπο.** Δεν υπάρχει «τελευταίος επιτυχημένος έλεγχος» πουθενά.
- **Δύο ιστορικά περιστατικά (13/9 σημάδια σύγκρουσης στον κώδικα, 5/9 παλιό cache) θα τα είχε πιάσει ένας αυτόματος μηχανικός έλεγχος κειμένου πριν το push — χωρίς μοντέλο ΑΙ** — που δεν υπάρχει ακόμη. Είναι το μόνο «θα το είχε πιάσει» που ισχύει, γιατί το αποδεικτικό είναι η ίδια η αλλαγή.

## 2. Τι χρειάζεται να κατασκευαστεί (πριν από οποιοδήποτε bot)

| Τι | Γιατί | Μέγεθος |

| **Ρόλος βάσης μόνο-ανάγνωσης** (`tms_monitor`: SELECT σε λίστα + INSERT μόνο στον πίνακα αποτελεσμάτων) | Χωρίς αυτόν, κάθε «ανάγνωση» γίνεται με κλειδί που μπορεί και να γράψει | 1 migration |
| **Σταθερός έλεγχος στη βάση** (`pg_cron` + schema `monitoring` + function) | 40 SQL έλεγχοι που τρέχουν μόνοι τους στις 03:00 και γράφουν πράσινο/κόκκινο/γκρι + ώρα | 1 migration |

Προαιρετικά αργότερα: ρόλος `auditor` στο TMS (μόνο αν αποφασιστεί πλοήγηση bot), έκδοση front end μέσα στα σφάλματα.

## 3. Τι ακριβώς θα κάνει καθημερινά το Grok (ή όποιος agent)

**Δύο ρόλοι, μόνο ανάγνωση, τίποτα άλλο:**

1. **Ελεγκτής αλλαγών** (προτεραιότητα, μηδέν ρίσκο): σε κάθε push/PR διαβάζει το diff με τα δύο εγχειρίδια και απαντά «τι σπάει επιχειρησιακά, ποια κλειδωμένη απόφαση παραβιάζεται, ποιες σελίδες επηρεάζονται, τι δεν δοκιμάστηκε». Δεν χρειάζεται πρόσβαση σε βάση ή logs. Πριν εμπιστευτούμε την κρίση του, **μετριέται** σε 7 παλιά περιστατικά + 5 σωστές αλλαγές, χωρίς να του δίνεται η λύση (`04` §1Γ).
2. **Πακέτα διάγνωσης**: για κάθε **νέο** κόκκινο του σταθερού ελέγχου παίρνει ένα μικρό πακέτο (το αποτέλεσμα, λίγες εγγραφές, το σχετικό κομμάτι εγχειριδίου) και παραδίδει: τι περιμέναμε / τι είδαμε / πιθανή αιτία / εναλλακτικές / ασφαλή βήματα επιβεβαίωσης / ποιος αποφασίζει. **Ποτέ** διόρθωση, **ποτέ** δεν γυρίζει κόκκινο σε πράσινο.

Πρωινή αναφορά στα ελληνικά, ≤ 1 οθόνη, με υποχρεωτική γραμμή «τελευταίος επιτυχημένος έλεγχος». Ειδοποίηση μόνο για νέο σημαντικό, επιδείνωση, ή όταν **ο ίδιος ο μηχανισμός** δεν έτρεξε. Ονόματα εργαζομένων ποτέ. Η «ανάλυση χρήσης» είναι δεύτερη φάση, όχι μέρος του πιλότου.

## 4. Τι θα κάνει το σταθερό σύστημα (χωρίς μοντέλο)

Κάθε νύχτα στις 03:00, 40 έλεγχοι SQL (`02`): διαθεσιμότητα, σφάλματα, ιστορικό, Weekly, εθνικά σκέλη/ράμπα, αναθέσεις, έξοδα/μισθοδοσία/τιμολόγηση/παλέτες, μετά από deploy. Κάθε έλεγχος γράφει **πράσινο / κόκκινο / γκρι** και την ώρα. **Γκρι = δεν ελέγχθηκε** (π.χ. Cloudflare χωρίς πρόσβαση, `app_errors` σε σιωπή) — ποτέ πράσινο από υπόθεση. Οι εξαιρέσεις της επιχείρησης (national_orders άδειο, σκέλη split, ιστορικό Excel, 2 τιμολόγια 21/8, εβδομάδα Σάββατο–Παρασκευή) είναι **μέσα** στους ελέγχους, όχι στην κρίση του agent. Κόστος: 0 €, δευτερόλεπτα ανά νύχτα.

## 5. Κόστος και αβεβαιότητες

- **Πρόταση: μόνο υπάρχουσες συνδρομές, καμία νέα αγορά, καμία αλλαγή χρέωσης.**
- Σταθερός έλεγχος, αποθήκευση, CI: **0 €** στα σημερινά πλάνα (η βάση < 20 MB· τα όρια του πλάνου Supabase/CF **δεν επαληθεύτηκαν**).
- Agent ρόλος 1: εκτίμηση **25–40k tokens ανά αξιολόγηση**, ~3 push/ημέρα → ~100k/ημέρα (**παραδοχή**: ~3 bytes/token ελληνικά). Ρόλος 2: 0–2 διαγνώσεις/ημέρα × ~15k. Με Claude Code: μέσα στην υπάρχουσα συνδρομή (όρια πλάνου **δεν επαληθεύτηκαν**). Με Grok: συνδρομή/τιμολόγηση **δεν επαληθεύτηκαν**. Hermes: **δεν επαληθεύτηκε**.
- Εφάπαξ: ~1 ημέρα developer για migrations + CI script. Συντήρηση: ~1 ώρα/εβδομάδα ανθρώπου για τα εγχειρίδια.
- **Το ακριβό μέρος είναι ο άνθρωπος** (βαθμολόγηση benchmark, απόφαση σε κάθε κόκκινο), όχι τα tokens.
- Αβεβαιότητες που μένουν: γιατί σιωπά το `app_errors`· γιατί τα console.error του Worker δεν φαίνονται στο CF· αν το Grok τρέχει server-side· ποιο νούμερο είναι «οι μπλοκαρισμένες πύλης» (159/167/60).
