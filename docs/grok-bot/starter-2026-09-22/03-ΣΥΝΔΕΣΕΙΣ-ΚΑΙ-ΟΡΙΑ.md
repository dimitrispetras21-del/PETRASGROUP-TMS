# Συνδέσεις και όρια — πώς περιορίζεται ΤΕΧΝΙΚΑ ο ελεγκτής σε μόνο-ανάγνωση (για τον ιδιοκτήτη, 22/9/2026)

**Η αρχή:** η οδηγία «μην αλλάξεις τίποτα» στο prompt **δεν είναι όριο δικαιωμάτων**. Είναι ευγενική παράκληση σε ένα μοντέλο. Όριο είναι μόνο ό,τι επιβάλλει το κλειδί: ό,τι δεν επιτρέπει το κλειδί, δεν γίνεται· ό,τι επιτρέπει, **θα γίνει κάποια μέρα**. Γι' αυτό κάθε σύνδεση παρακάτω περιορίζεται στο κλειδί, και η επαλήθευση γίνεται **χωρίς καμία δοκιμαστική εγγραφή**.

## Α. GitHub — ΠΡΩΤΟ, μπορεί να γίνει σήμερα

**Τι χρειάζεται ο ελεγκτής:** ανάγνωση αρχείων, commits, diffs, branches και PR του ενός repo. Τίποτα άλλο.

**Πώς περιορίζεται (επιλογή 1 — fine-grained PAT, προτείνεται):**
1. GitHub → Settings → Developer settings → Personal access tokens → Fine-grained tokens → Generate new token.
2. Token name: `grok-reviewer-readonly`. Expiration: ≤ 90 ημέρες (θα το ξαναφτιάξεις — καλό).
3. Resource owner: ο λογαριασμός σου. **Repository access: Only select repositories → `PETRASGROUP-TMS`.**
4. Repository permissions: **Contents: Read-only** · **Metadata: Read-only** (μπαίνει αυτόματα) · **Pull requests: Read-only**. Όλα τα άλλα «No access». Account permissions: κανένα.
5. Generate → αντιγραφή **μόνο** στον connector του Grok.

**Επιλογή 2 — GitHub App** με τα ίδια τρία Read permissions, εγκατεστημένη μόνο σε αυτό το repo. Ισοδύναμη· περισσότερη δουλειά. Μόνο αν το Grok το απαιτεί.

**Τι ΔΕΝ δίνεις:** classic token με `repo` scope (γράφει)· Workflows· Administration· Secrets· Actions· οποιοδήποτε Write.

**Επαλήθευση χωρίς εγγραφή:**
- Στη σελίδα του token (Settings → Fine-grained tokens → το token) βλέπεις: 1 repository, 3 permissions, όλα Read.
- Μέσω API (ο Grok ή εσύ με curl): `GET https://api.github.com/repos/dimitrispetras21-del/PETRASGROUP-TMS` με το token → στο JSON το πεδίο `permissions` πρέπει να έχει `"push": false, "admin": false, "maintain": false, "pull": true`. Αν `push` είναι `true`, το token γράφει — το ανακαλείς.
- `GET https://api.github.com/repos/dimitrispetras21-del/PETRASGROUP-TMS/commits/main` → `sha` που ξεκινά με `55f101c` (22/9) ή νεότερο.
- Σημείωση: το header `x-oauth-scopes` υπάρχει μόνο σε classic tokens· για fine-grained η επαλήθευση είναι η σελίδα του token + το `permissions` παραπάνω.

**Τι μένει άγνωστο:** αν ο connector του Grok αποθηκεύει το token με ασφάλεια — εκτός ελέγχου μας· γι' αυτό μόνο Read και μικρή λήξη. Το repo είναι δημόσιο: ένα διαρρεύσαν Read token δεν αποκαλύπτει τίποτα, ένα Write token θα μπορούσε να αλλάξει την παραγωγή (Pages = main).

## Β. Supabase — ΚΛΕΙΣΤΟ μέχρι να υπάρξει ρόλος μόνο-ανάγνωσης

**Τι χρειάζεται ο ελεγκτής:** `SELECT` σε ρητή λίστα πινάκων/όψεων, με χρονικό όριο ανά query. Τίποτα άλλο.

**Τα τρία είδη «κλειδιού» Supabase — και γιατί μόνο ένα κάνει:**

| Είδος | Τι είναι | Περιορίζεται σε μόνο-ανάγνωση; |
|---|---|---|
| **Connection string Postgres** με **δικό του ρόλο** (`tms_reader`) | Κανονική σύνδεση βάσης με χρήστη/κωδικό | **ΝΑΙ** — με GRANT μόνο SELECT. **Η μόνη αποδεκτή.** |
| `service_role` key / `anon` key (PostgREST) | Κλειδιά API του project | **ΟΧΙ.** `service_role` = τα πάντα. `anon` = ό,τι έχουν grant οι ρόλοι `anon`/`authenticated` (RLS ενεργό, 0 policies· grants μετρήθηκαν 0 στις 22/9, default privileges ΔΕΝ ελέγχθηκαν — «σήμερα δεν βλέπει τίποτα» ≠ «είναι μόνο-ανάγνωσης»). |
| **Management API token / PAT** (`sbp_…`, Account → Access Tokens) | Token διαχείρισης λογαριασμού (τρέχει SQL ως διαχειριστής, αλλάζει ρυθμίσεις, φτιάχνει projects) | **ΟΧΙ — δεν περιορίζεται.** Ισοδύναμο με τον κωδικό σου. Αν ο connector του Grok ζητά αυτό, **δεν συνδέεις** τη βάση. |

**Έλεγχος που κάνεις εσύ, πριν από οτιδήποτε:** άνοιξε τη ρύθμιση του connector Supabase στο Grok Bot και δες τι ζητά — (α) «connection string / host, user, password» → μπορεί να γίνει με `tms_reader`· (β) «access token» / «personal access token» / `sbp_` → **όχι**· (γ) «project URL + API key» → **όχι** (service_role/anon). Στείλε στον συντονιστή τι είδες — **όχι** τις τιμές.

### DRAFT SQL — ρόλος `tms_reader` (πρόταση, ΔΕΝ εκτελέστηκε, δεν εκτελείται από κανένα agent)

```sql
-- DRAFT 22/9/2026 — ρόλος μόνο-ανάγνωσης για τον ανεξάρτητο ελεγκτή.
-- Εκτελείται ΜΟΝΟ από τον ιδιοκτήτη, στο SQL editor, μετά τις 15:00, μέσα σε ΜΙΑ συναλλαγή.
-- Αναστρέψιμο: DROP OWNED BY tms_reader; DROP ROLE tms_reader;

BEGIN;

-- 1. Ο ρόλος: μπορεί να συνδεθεί, τίποτα άλλο. Ο κωδικός μπαίνει τη στιγμή της εκτέλεσης, δεν γράφεται πουθενά.
CREATE ROLE tms_reader LOGIN PASSWORD '<ΒΑΛΕ-ΙΣΧΥΡΟ-ΚΩΔΙΚΟ>'
  NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS NOREPLICATION
  CONNECTION LIMIT 2;

-- 2. Ζώνη ασφαλείας (ΟΧΙ όριο δικαιωμάτων — ο ρόλος μπορεί να τα αλλάξει στη session του· το πραγματικό όριο είναι τα GRANT στο βήμα 4).
ALTER ROLE tms_reader SET default_transaction_read_only = on;
ALTER ROLE tms_reader SET statement_timeout = '5s';
ALTER ROLE tms_reader SET idle_in_transaction_session_timeout = '10s';
ALTER ROLE tms_reader SET search_path = public;

-- 3. Πρόσβαση στο schema, χωρίς δικαίωμα δημιουργίας αντικειμένων.
GRANT USAGE ON SCHEMA public TO tms_reader;
REVOKE CREATE ON SCHEMA public FROM tms_reader;

-- 4. ΜΟΝΟ SELECT, ΜΟΝΟ σε ρητή λίστα. Όχι «ON ALL TABLES»: ό,τι γεννιέται, γεννιέται κλειστό (αρχή 5).
--    Λίστα από CLAUDE.md + migrations 22/9 — ο ιδιοκτήτης επιβεβαιώνει τα ονόματα πριν εκτελέσει:
--    select table_name from information_schema.tables where table_schema='public' order by 1;
GRANT SELECT ON
  orders, national_orders, national_loads, order_stops, groupage_lines, consolidated_loads,
  partner_assignments, ramp, fuel, pallet_ledger_suppliers, pallet_ledger_partners,
  workshops, maint_history, maint_req, maint_plan, clients, partners, locations,
  drivers, trucks, trailers, countries, local_moves,
  ct_round_trips, ct_rt_legs, ct_cost_docs, ct_cost_lines, ct_settings, ct_import_rules, ct_plate_aliases,
  dl_entries, dl_import_batches, pl_movements,
  app_errors, facade_unknown_fields
TO tms_reader;

-- Όψεις ελέγχου (μόνο ανάγνωση εκ φύσεως):
GRANT SELECT ON
  orders_with_derived, ct_v_rt_pnl, ct_v_rt_costs, ct_v_rt_revenue, ct_v_rt_pallet_gate,
  ct_v_fuel, ct_v_consumption, ct_v_wear_rate,
  dl_v_entries, dl_v_balance, dl_v_rt_gap, dl_v_rt_route,
  pl_v_balance_clients, pl_v_balance_partners, pl_v_order_gate, pl_v_client_locations,
  v_client_delivery, v_driver_delivery, v_partner_delivery, maint_plan_status
TO tms_reader;

-- audit_log: ΧΩΡΙΣ before_data/after_data (περιέχουν πλήρεις εγγραφές με προσωπικά) — column-level grant.
--   ΑΠΟΦΑΣΗ ΙΔΙΟΚΤΗΤΗ: ο έλεγχος ΣΤ1 του 02-έλεγχοι.md διαβάζει after_data->>'split'. Αν το θέλεις, πρόσθεσε after_data.
--   Τα ονόματα στηλών να επιβεβαιωθούν: select column_name from information_schema.columns where table_name='audit_log';
GRANT SELECT (id, created_at, actor, role, action, table_name, record_id) ON audit_log TO tms_reader;

-- users: ΚΑΝΕΝΑ δικαίωμα (password hashes). Αν χρειαστεί «πόσοι ενεργοί ανά ρόλο», column-level μόνο σε (username, role, active) — ξεχωριστή απόφαση.

-- 5. Συναρτήσεις: στην Postgres το EXECUTE δίνεται σε PUBLIC από προεπιλογή. Ένας SELECT-only ρόλος ΜΠΟΡΕΙ να καλέσει
--    συνάρτηση που γράφει (π.χ. SECURITY DEFINER). Το σκληρό κλείσιμο (REVOKE EXECUTE … FROM PUBLIC + GRANT πίσω σε
--    service_role/postgres/authenticated όπου χρειάζεται) αγγίζει και τον Worker — ΞΕΧΩΡΙΣΤΗ migration, αφού μετρηθεί:
--    select proname, prosecdef from pg_proc where pronamespace = 'public'::regnamespace order by 1;
--    Μέχρι τότε ο κανόνας «καμία συνάρτηση/RPC σε SELECT» του prompt είναι ΜΑΛΑΚΟ όριο και ο ιδιοκτήτης το ξέρει.

-- 6. Τίποτα από τα μελλοντικά: κανένα ALTER DEFAULT PRIVILEGES για tms_reader. Νέος πίνακας = κλειστός μέχρι ρητό GRANT.

COMMIT;
```

**Τι ακριβώς εγκρίνεις (ναι/όχι σε καθένα):**
1. Δημιουργία ρόλου `tms_reader` με LOGIN, χωρίς superuser/createrole/bypassrls, όριο 2 συνδέσεις.
2. SELECT **μόνο** στους πίνακες και τις όψεις της λίστας (τα ονόματα τα επιβεβαιώνεις εσύ με το `information_schema` query πριν).
3. `audit_log` **χωρίς** `before_data/after_data` — ή **με** `after_data` (τότε ο ελεγκτής βλέπει περιεχόμενο εγγραφών).
4. `users`: **κανένα** δικαίωμα.
5. Οι συναρτήσεις μένουν ανοιχτές προς το παρόν (μαλακό όριο) — ή ζητάς ξεχωριστό DRAFT για σκληρό κλείσιμο.
6. Ο κωδικός: τον βάζεις εσύ, τον δίνεις **μόνο** στον connector, πουθενά αλλού· αλλαγή με `ALTER ROLE tms_reader PASSWORD …` όποτε θέλεις.

**Σύνδεση:** Supabase Dashboard → Connect → η μορφή που δείχνει (pooler ή direct)· αντικαθιστάς χρήστη με `tms_reader` (στο pooler η μορφή χρήστη είναι `tms_reader.<project-ref>` — όπως το δείχνει το dashboard) και κωδικό. **Ποτέ** το string του `postgres` ή του `service_role`.

**Επαλήθευση μόλις συνδεθεί (ο Grok τα τρέχει πρώτα, τα τυπώνει, καμία εγγραφή):**
```sql
select current_user, current_setting('transaction_read_only') as ro, current_setting('statement_timeout') as st;
-- αναμένεται: tms_reader | on | 5s
select rolsuper, rolcreaterole, rolcreatedb, rolbypassrls, rolcanlogin from pg_roles where rolname = current_user;
-- αναμένεται: f | f | f | f | t
select has_table_privilege(current_user, 'public.orders', 'SELECT') as sel_orders,
       has_table_privilege(current_user, 'public.orders', 'INSERT') as ins_orders,
       has_table_privilege(current_user, 'public.orders', 'UPDATE') as upd_orders,
       has_table_privilege(current_user, 'public.orders', 'DELETE') as del_orders,
       has_table_privilege(current_user, 'public.users',  'SELECT') as sel_users;
-- αναμένεται: t | f | f | f | f
select count(*) as non_select_grants from information_schema.role_table_grants
 where grantee = current_user and privilege_type <> 'SELECT';
-- αναμένεται: 0
```
Οποιαδήποτε απόκλιση → η σύνδεση δεν χρησιμοποιείται, ενημερώνεται ο συντονιστής.

**Τι μένει άγνωστο:** αν το Grok Bot δέχεται καθόλου connection string με δικό του ρόλο· αν το πλάνο Supabase επιτρέπει σύνδεση από τη διεύθυνση του Grok (IP allowlist/pooler)· αν οι `default privileges` του project δίνουν κάτι σε PUBLIC που θα κληρονομούσε ο ρόλος (έλεγχος: `select * from information_schema.role_table_grants where grantee='PUBLIC'`).

## Γ. Cloudflare — ΚΛΕΙΣΤΟ μέχρι P1· μετά μόνο μεταδεδομένα

**Γιατί κλειστό σήμερα (γεγονός):** `worker/wrangler.toml:36-37` έχει `[observability] enabled = true` και **τίποτα** άλλο — δεν υπάρχει `[observability.logs] invocation_logs = false`. Με αυτή τη ρύθμιση η Cloudflare καταγράφει **αυτόματα** ένα invocation log ανά αίτημα με το πλήρες request, μαζί με τα headers — άρα και το `Authorization: Bearer <JWT>` κάθε χρήστη (8 ωρών). Ο ίδιος ο Worker **δεν** γράφει headers (54 `console.*` κλήσεις στο `worker/src/index.js`, καμία με headers/token — έλεγχος 22/9)· η έκθεση είναι η αυτόματη καταγραφή. Retention 7 ημέρες. Επιφύλαξη: το `main` ≠ deployed — αν η ρύθμιση άλλαξε στο dashboard χωρίς commit, δεν το ξέρουμε (και αυτό θα ήταν split-brain).

**Συνέπεια:** όποιος διαβάζει Workers Logs, διαβάζει ζωντανά tokens χρηστών. Άρα **κανένα token με Logs/Observability Read σε bot** μέχρι: (1) εφαρμογή του `docs/grok-bot/08-P1-header-redaction-DRAFT.md` (επιλογή i: `invocation_logs = false` + deploy μετά τις 15:00 με φρουρό των τριών), (2) 7 ημέρες αναμονή για να λήξουν τα παλιά logs.

**Τι χρειάζεται ο ελεγκτής (μετά το P1):** μόνο «ποια έκδοση/ημερομηνία deploy έχει ο Worker `petras-tms-backend-staging`» — για να συγκρίνει με το `main`.

**Πώς περιορίζεται:** Cloudflare Dashboard → My Profile → API Tokens → Create Token → **Custom token**:
- Permissions: **Account → Workers Scripts → Read**. Προαιρετικά **Account → Account Analytics → Read**. **Τίποτα Edit. Τίποτα Logs / Observability / Workers Tail / Logpush** μέχρι το P1.
- Account Resources: **Include → μόνο ο λογαριασμός του TMS** (account id στο `wrangler.toml:10`). Zone Resources: **κανένα**.
- Client IP filtering: αν ξέρεις τη διεύθυνση του Grok, βάλ' την. TTL: ημερομηνία λήξης.
- **ΟΧΙ** Global API Key. **ΟΧΙ** τα templates «Edit Cloudflare Workers». **ΟΧΙ** το token που χρησιμοποιείς εσύ για deploy (`CF_API_TOKEN` του `.env.local`).

**Επαλήθευση χωρίς εγγραφή:**
- `GET https://api.cloudflare.com/client/v4/user/tokens/verify` με `Authorization: Bearer <token>` → `"status": "active"` και το `id` του token.
- Στο dashboard, η γραμμή του token δείχνει τα permission groups: πρέπει να είναι μόνο «Workers Scripts Read» (+ «Account Analytics Read»). Μέσω API: `GET /client/v4/user/tokens/<id>` → `policies[].permission_groups[].name` — κανένα με «Write», «Edit», «Logs», «Observability».
- Δοκιμή ανάγνωσης: `GET /client/v4/accounts/<account_id>/workers/scripts` → λίστα με `petras-tms-backend-staging` και `modified_on`.

**Τι μένει άγνωστο:** τι είδους διαπιστευτήριο χρησιμοποιεί σήμερα ο connector Cloudflare του Grok (token με ποια permissions; Global key;) — **έλεγξέ το τώρα** στο Grok και, αν είναι Global API Key ή token με Edit/Logs, **αφαίρεσέ το** μέχρι να φτιαχτεί το παραπάνω. Επίσης αν το Grok τρέχει server-side (τότε τα κλειδιά ζουν σε ξένο server).

## Δ. Η εφαρμογή TMS (browser) — ΚΑΝΕΝΑΣ λογαριασμός

Δεν υπάρχει ρόλος TMS μόνο-ανάγνωσης. Ο πιο κοντινός (`warehouse`) γράφει παλέτες· ο `management` γράφει. Η δημιουργία ρόλου `auditor` (`"*": ["GET"]` στον Worker, χωρίς καμία γραμμή write, + εγγραφή στο `users` + roster σε `config.js`/`index.html`) είναι **τρία σημεία και ένα deploy** — ξεχωριστή απόφαση, όχι μέρος αυτού του πακέτου. Μέχρι τότε: **κανένα login**. Ακόμη και με τέτοιο ρόλο, οι σελίδες «Πίνακας Ράμπας» (`modules/daily_ramp.js:95`, γράφει στο άνοιγμα) και «Εθνικές Παραλαβές» (`core/router.js:358`, iframe άγνωστης συμπεριφοράς) μένουν απαγορευμένες.

## Ε. Σύνοψη: τι είναι απαραίτητο ΤΩΡΑ, τι είναι βελτίωση

| | Απαραίτητο για να ξεκινήσει | Βελτίωση αργότερα |
