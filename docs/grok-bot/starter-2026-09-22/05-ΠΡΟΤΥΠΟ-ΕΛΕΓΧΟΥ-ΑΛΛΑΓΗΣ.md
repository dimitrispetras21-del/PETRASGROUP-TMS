# Πρότυπο ελέγχου αλλαγής — επαναχρησιμοποιήσιμο (έκδοση 22/9/2026)

*Ο συντονιστής συμπληρώνει τα `<…>` των ενοτήτων Α–Δ και στέλνει το κείμενο κάτω από τη γραμμή στον Grok (μετά το `01` και το `02`). Την ενότητα Ζ τη συμπληρώνει ο συντονιστής **αφού** λάβει την αναφορά — ποτέ πριν. Το πρότυπο δεν αλλάζει από τον Grok.*

**Αρχή σειράς:** ο ελεγκτής σχηματίζει **ανεξάρτητη** κρίση από τον κώδικα και τους κανόνες **πρώτα**· οι ισχυρισμοί του συγγραφέα (commit messages, docs της αλλαγής, screenshots) διαβάζονται **τελευταίοι** και συγκρίνονται. Ό,τι ο ελεγκτής προτείνει ως νέο έλεγχο **δεν εγκαθίσταται** από κανέναν αυτόματα — είναι πρόταση προς τον ιδιοκτήτη.

## Δ. Κώδικας και εξαρτήσεις που πρέπει να ανοιχτούν (στο SHA της κεφαλής)
- Τα αρχεία του diff.
- Callers/callees: για κάθε συνάρτηση που αλλάζει ή αφαιρείται, **grep** σε `core/` και `modules/` ποιος την καλεί (και `window.*` exports).
- Χάρτης πεδίων: `worker/src/index.js` `TABLES.<πίνακας>.fields/aliases` για κάθε label που γράφεται/διαβάζεται (μονολεκτικά χωρίς εισαγωγικά!).
- Δικαιώματα: `PERMISSIONS` / `COSTS_PERMS` / `PL_PERMS` για κάθε (ρόλος, πίνακας, μέθοδος) που αγγίζει η αλλαγή.
- Βάση: migrations που η αλλαγή προϋποθέτει (`worker/migrations/*.sql` — κεφαλίδα DRAFT/ΕΚΤΕΛΕΣΤΗΚΕ) και triggers που θα τρέξουν.
- Εκδόσεις: `app.html` `?v=` των modules που άλλαξαν + `sw.js` `SW_VERSION`.
- Tests/rigs που υπάρχουν για το module (`tests/`, `tests/critics/`) — **δεν τα τρέχεις**· λες αν υπάρχουν και αν καλύπτουν την αλλαγή.

## Ε. Τι πρέπει να απαντήσει ο ελεγκτής (η αναφορά)

Στο format του system prompt §10, με επιπλέον:

**Ε1. Μηχανικά** (καθένα pass / fail / n.a. με αρχείο:γραμμή):
- Μ1 conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`) σε κάθε αρχείο του diff
- Μ2 σύνταξη JS (ανάγνωση· αν ο connector επιτρέπει `node --check` χωρίς άλλες παρενέργειες, μόνο αυτό)
- Μ3 bump `?v=` + `SW_VERSION` μέσα στο εύρος
- Μ4 κάθε νέο label πεδίου υπάρχει στον χάρτη `TABLES` του σωστού πίνακα
- Μ5 κάθε νέο write (ρόλος, πίνακας, μέθοδος) επιτρέπεται στο `PERMISSIONS`
- Μ6 νέο `fetch/catch` που σιωπά (catch χωρίς toast/logError)
- Μ7 υπάρχουν rigs/tests για το module — καλύπτουν τη νέα συμπεριφορά;
- Μ8 migration στο diff → κεφαλίδα δηλώνει κατάσταση + ημερομηνία

**Ε2. Πέντε ερωτήσεις κρίσης:**
1. Παραβιάζει κλειδωμένη απόφαση (`02` §7); Ποια, πού.
2. Ποιες **άλλες** σελίδες/callers επηρεάζονται (με grep, όχι υπόθεση);
3. Τι γίνεται με τα **ιστορικά δεδομένα** (γραμμές πριν την αλλαγή — NULL, παλιές τιμές, σημάνσεις);
4. Ποιες περιπτώσεις **δεν δοκιμάστηκαν** (ιδίως: φόρμα παραγγελιών ανοιγμένη; γράφτηκε όντως στη βάση;);
5. Ποια **σιωπηλή αποτυχία** μπορεί να προστεθεί (μηχανισμοί #1/#2/#3 του `02` §5β);

**Ε3. Συγκεκριμένα σενάρια αποτυχίας** — για καθένα: συμβαίνει; (ΓΕΓΟΝΟΣ/ΥΠΟΘΕΣΗ) · ποιος ρόλος · ποια οθόνη · τι βλέπει ή τι δεν γράφεται · επίπτωση στη δουλειά της ημέρας:
- `<σενάριο 1 από τον συντονιστή>`
- `<σενάριο 2>`
- + όσα εντοπίσει ο ελεγκτής μόνος του.

**Ε4. Κάλυψη ελέγχων:** καλύπτουν οι υπάρχοντες έλεγχοι (rigs, critics, όψεις ελέγχου της βάσης, `docs/grok-bot/02-έλεγχοι.md`) τη νέα συμπεριφορά; Έγινε κάποιος παλιός έλεγχος ανεπαρκής ή βασίζεται πια σε λάθος παραδοχή; Συμφωνεί η τεκμηρίωση (`CLAUDE.md`, `DECISION_LOG`, `02`) με την υλοποίηση;

**Ε5. Ελλείποντα στοιχεία:** τι θα χρειαζόταν για να γίνει ΓΕΓΟΝΟΣ κάθε ΥΠΟΘΕΣΗ (ποιο SELECT, ποιο άνοιγμα οθόνης, ποια έκδοση Worker) — χωρίς να το κάνεις.

**Ε6. Προτάσεις νέων ελέγχων** (πρόταση, δεν εγκαθίσταται): για κάθε νέα συμπεριφορά χωρίς κάλυψη — τι θα μετρούσε ο έλεγχος, πού (SQL / rig / μηχανικό grep), ποιο κόκκινο θα έδινε. Μία γραμμή ανά πρόταση.

**Ε7. ΔΕΝ ΕΛΕΓΧΘΗΚΕ & γιατί** — ποτέ κενό. Πάντα περιλαμβάνει: «η έκδοση του Worker στην παραγωγή μού είναι άγνωστη».

**Ε8. ΕΚΤΕΛΕΣΤΗΚΑΝ** — κάθε SQL αυτούσιο, κάθε HTTP GET, κάθε αρχείο/commit που διαβάστηκε.

## ΣΤ. Ισχυρισμοί συγγραφέα — διαβάζονται ΜΕΤΑ την αναφορά
Αφού γράψεις τα Ε1–Ε8, διάβασε τα commit messages του εύρους και ό,τι doc της αλλαγής σου δώσει ο συντονιστής. Για κάθε ισχυρισμό: ΕΠΑΛΗΘΕΥΤΗΚΕ / ΔΙΑΨΕΥΣΤΗΚΕ / ΔΕΝ ΕΠΑΛΗΘΕΥΤΗΚΕ + πώς. Ισχυρισμοί για ζωντανές δοκιμές, screenshots, probes, «0 PATCH», «rig N/N» **δεν** επαληθεύονται από τον κώδικα — το λες, δεν τους υιοθετείς. Αν η δική σου κρίση διαφέρει από του συγγραφέα, **δεν** την αλλάζεις — γράφεις τη διαφορά.
