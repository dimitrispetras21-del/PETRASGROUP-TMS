## Τι ΔΕΝ γνωρίζουμε (δεν επαληθεύτηκε 22/9)

- Grok Bot: αν τρέχει server-side ή τοπικά, αν κρατά project instructions μεταξύ ημερών, πώς περιορίζει τους connectors (read scopes;), τιμολόγηση, ποιο repo/έργο/λογαριασμό βλέπει κάθε connector (πρέπει να το επιβεβαιώσει ο owner με τα 3 tests του `03-σχέδιο-σύνδεσης.md`).
- Hermes Agent: ωριμότητα, απομόνωση δικαιωμάτων, κόστος. Καμία δοκιμή.
- Καμία από τις τρεις επιλογές δεν πέρασε το benchmark του `04-πιλότος.md` — **δεν έχει τρέξει**. Οποιοσδήποτε ισχυρισμός «θα το είχε πιάσει» είναι ανεπαλήθευτος.
- Το repo δεν περιέχει καμία αναφορά σε «grok» ή «hermes» (grep 22/9).

## Μία προειδοποίηση

Περισσότερη μνήμη, plugins ή «πιο έξυπνο» μοντέλο **δεν** σημαίνει καλύτερη κρίση για *αυτό* το σύστημα. Το TMS έχει δεκάδες τεκμηριωμένες εξαιρέσεις. Ένας agent χωρίς τις εξαιρέσεις θα «βρίσκει» καθημερινά ψεύτικα προβλήματα — και ένας agent που τις ξέρει αλλά **δεν** έχει τεχνικά όρια θα τις «διορθώσει» κάποια μέρα μόνος του. Η αξία είναι στα **γραπτά εγχειρίδια + σταθερούς ελέγχους + κλειδιά μόνο-ανάγνωσης** — όποιο μοντέλο κι αν διαβάζει.

## Πρόταση (για απόφαση owner, όχι ενεργοποίηση)

1. **Πρώτος πιλότος = Ρόλος 1 με την επιλογή Γ** (Claude Code session, χειροκίνητη εκκίνηση σε κάθε push από τον συντονιστή). Γιατί: 0 € πρόσθετο, τα εγχειρίδια υπάρχουν, **μηδέν** πρόσβαση σε βάση/CF χρειάζεται (μόνο το diff), άρα μηδέν ρίσκο. Μετριέται με το benchmark του 04 **πριν** αποφασιστεί κάτι άλλο.
2. **Grok Bot ή Hermes για τον ίδιο ρόλο μόνο ως σύγκριση**, με το ίδιο benchmark, χωρίς connectors βάσης/CF. Αν κάποιος από τους τρεις πιάνει περισσότερα με λιγότερους ψευδείς συναγερμούς, κερδίζει.
3. **Ρόλος 2 (διαγνώσεις)**: σε καμία επιλογή πριν υπάρξουν ο ρόλος `tms_monitor` και ο πίνακας `monitoring.health_checks`. Χωρίς αυτά, κάθε «διάγνωση» τρέχει με κλειδιά που γράφουν.
