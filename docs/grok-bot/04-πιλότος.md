## 1. ΡΟΛΟΣ 1 — Έλεγχος προτεινόμενων αλλαγών (προτεραιότητα)

**Πότε:** (α) **πριν** περάσει μια αλλαγή στη ζωντανή εφαρμογή (PR ή branch)· (β) **συμπληρωματικά** για push απευθείας στο `main` — όπως δουλεύουμε σήμερα (το Pages σερβίρει το `main` αμέσως, άρα το (β) ελέγχει **μετά** το γεγονός και μπορεί μόνο να ζητήσει revert).

**Τι παίρνει:** το diff (commit SHA ή PR), τα δύο εγχειρίδια (`skill-tms-knowledge.md`, `CLAUDE.md`), και **μόνο** τα αρχεία που το diff αγγίζει συν τους callers τους. Όχι πρόσβαση σε βάση, CF, ή κλειδιά. **Μηδέν ρίσκο** στα δεδομένα.

### 1Β. Αξιολόγηση agent — επιχειρησιακή κρίση (μετά τα μηχανικά)

Ο agent διαβάζει το diff με τα εγχειρίδια και απαντά **μόνο** σε αυτά:

| Ερώτηση | Παράδειγμα από το ιστορικό |
|---|---|
| Παραβιάζει **κλειδωμένη απόφαση** (CLAUDE.md §κλειδωμένες, DECISION_LOG); | Αλλαγή που γράφει `national_orders` από Veroia Switch· «διόρθωση» του `Net Price`· cutoff στην πύλη παλετών |
| Ποιες **άλλες σελίδες/callers** επηρεάζει; (grep callers της συνάρτησης) | Ενοποίηση φορμών 10/8 (`be2fa5b` → revert `68ecbf4` σε 2΄): το κουμπί groupage-επεξεργασίας δρομολογήθηκε στον writer δημιουργίας → διπλότυπα σε 4 πίνακες |
| Τι γίνεται με τα **ιστορικά δεδομένα**; (γραμμές πριν την αλλαγή — NULL, παλιές τιμές) | 038: 302→175 γραμμές — ένα diff που αλλάζει σχήμα χωρίς πριν/μετά μέτρηση |
| Ποιες **περιπτώσεις δεν δοκιμάστηκαν**; (φόρμα παραγγελιών χωρίς άνοιγμα = απαγορεύεται, CLAUDE.md) | 10/8 ξανά |
| Τι **σιωπηλή αποτυχία** μπορεί να προσθέσει; (catch χωρίς logError, `if (column)` χωρίς else) | Μηχανισμός #1 |

**Δέσιμο κάθε αξιολόγησης:** `commit SHA` + `hash των 2 εγχειριδίων` + ημερομηνία. Νέος κώδικας ή νέο εγχειρίδιο = **η παλιά αξιολόγηση άκυρη**. Αποτέλεσμα σε markdown/JSON με πεδία: `sha, rules_hash, mechanical{Μ1..Μ8: pass/fail/skip}, findings[{question, severity, evidence(file:line), certainty}]`, διαβάσιμο από οποιονδήποτε.

6. Αποτέλεσμα: πίνακας 7×3 + 5×2. **Καμία υπόθεση πριν τρέξει.**

## 4. ΔΕΥΤΕΡΗ ΦΑΣΗ — Ανάλυση χρήσης (ΜΟΝΟ σχέδιο, δεν ανήκει στον πιλότο)

**Σκοπός: δυσκολίες διαδικασίας και χρήσης, ΟΧΙ βαθμολόγηση εργαζομένων.** Γράφεται ρητά, και ισχύει για κάθε αναφορά: ονόματα χρηστών **δεν** εμφανίζονται· μόνο ρόλοι και πλήθη.

**Τι καταγράφεται ΠΡΑΓΜΑΤΙΚΑ σήμερα** (01 §2–3): αιτήματα Worker (CF, 7 ημέρες, με status/διαδρομή, **χωρίς** ρόλο εκτός από το JWT-in-header που **δεν** θα διαβάζεται μετά P1) · επιτυχείς εγγραφές ανά ρόλο/πίνακα (`audit_log`) · σφάλματα browser χωρίς ρόλο (`app_errors`) · σιωπηλές απορρίψεις με ρόλο (`facade_unknown_fields`). **Δεν** καταγράφεται: ποια σελίδα άνοιξε ποιος, πόση ώρα έμεινε, τι είδε, τι προσπάθησε και δεν έστειλε.

**Ρητά ΔΕΝ εξισώνουμε:**

| Δεν λέμε | Γιατί |
|---|---|
| αίτημα Worker = ανθρώπινο κλικ | auto-refresh, preload cache 30 λεπτών (`core/api.js`), αλυσίδες `order-sync` (1 κλικ = 5–10 αιτήματα), OPTIONS preflight (το 49% των αιτημάτων) |
| επαναλαμβανόμενο άνοιγμα = εμπόδιο | μπορεί να είναι ροή εργασίας (Weekly ανοιχτό όλη μέρα) |
| απουσία εισόδου = απουσία εργασίας | κοινές συνεδρίες (JWT 8h σε ανοιχτή καρτέλα), δουλειά εκτός TMS (WEEKLY PLAN/KRONOS — CLAUDE.md: «ΠΟΤΕ ετήσια εικόνα από TMS») |
| χειροκίνητη γραμμή DKV = βέβαιο διπλό | ο φρουρός w11 (038/Ζ13) τα πιάνει· η χειροκίνητη μπορεί να είναι συμπλήρωση |
| `management` 0 ενέργειες = δεν χρησιμοποιεί | ο ρόλος διαβάζει· τα GET δεν καταγράφονται |

**Όπου λείπουν στοιχεία: «δεν επιτρέπεται ασφαλές συμπέρασμα».** Αν για να απαντηθεί ένα ερώτημα χρήσης χρειάζεται **νέα καταγραφή** (π.χ. page views ανά ρόλο, χρόνος σε σελίδα) → **ξεχωριστή πρόταση προς έγκριση** με τι συλλέγεται, για πόσο, ποιος το βλέπει — **όχι** μέρος του πιλότου.

Ερωτήματα που **μπορούν** να απαντηθούν με τα σημερινά στοιχεία (μετά P1): ποιες διαδρομές Worker γυρίζουν 4xx/5xx ανά ημέρα · ποιοι πίνακες γράφονται ανά ρόλο ανά εβδομάδα (audit) · πόσες σιωπηλές απορρίψεις ανά ρόλο (facade_unknown_fields) · ουρές εργασίας (ατιμολόγητες, χωρίς τιμή, πύλη παλετών) ως **τάση**, όχι ως πρόσωπο.

## 6. Μετρικές πιλότου (1 εβδομάδα) — τι μετράμε στο τέλος

| Μετρική | Πώς μετριέται | Στόχος εβδομάδας 1 (ΠΑΡΑΔΟΧΗ, όχι δέσμευση) |
|---|---|---|
| Επιβεβαιωμένα χρήσιμα ευρήματα | Ευρήματα που ο owner/συντονιστής χαρακτήρισε «ναι, το χρειαζόμασταν» (κατάσταση `investigating` ή `resolved_verified`) | ≥ 2 |
| Λανθασμένοι συναγερμοί | Ευρήματα που κατέληξαν `exception` ή «όχι πρόβλημα» / σύνολο ευρημάτων | ≤ 30% |
| Κάλυψη γνωστών ιστορικών προβλημάτων | Από το benchmark §1Γ: ΠΙΑΣΕ / 7 (χωρίς Π1 που είναι μηχανικό) | **μετριέται, δεν προβλέπεται** |
| Ψευδείς συναγερμοί benchmark | Από τα 5 καθαρά commits | **μετριέται** |
| Χρόνος διερεύνησης που εξοικονομείται | Για κάθε 🔴 με πακέτο: λεπτά που χρειάστηκε ο συντονιστής **με** το πακέτο vs εκτίμηση **χωρίς** (ίδιο πρόσωπο, καταγραφή στην ουρά) | αναφέρεται, δεν στοχεύεται |
| Χρήση/κόστος | tokens ανά αξιολόγηση (ρόλος 1) και ανά διάγνωση (ρόλος 2), από τον μετρητή του εργαλείου | ≤ 40k / ≤ 20k |
| Έλεγχοι που δεν ολοκληρώθηκαν (⚪) | `count(state='grey')` ανά ημέρα από `health_checks` — και **γιατί** (χωρίς πρόσβαση / απέτυχε / δεν ορίστηκε) | Το ⚪ μειώνεται μόνο με εγκρίσεις (P1, ρόλος readonly, ορισμοί) — **όχι** με «υπόθεση πράσινο» |
| Μηδέν μεταβολή δεδομένων | `audit_log` χωρίς actor του agent/ρόλου `tms_monitor` εκτός `monitoring.*` | **0, χωρίς εξαίρεση** |

**Κριτήριο συνέχισης:** αν στο τέλος της εβδομάδας τα χρήσιμα ευρήματα < 2 **ή** οι λανθασμένοι > 50% **ή** έστω μία μεταβολή δεδομένων → ο ρόλος σταματά και ξαναγράφονται τα εγχειρίδια/έλεγχοι, όχι ο agent.
