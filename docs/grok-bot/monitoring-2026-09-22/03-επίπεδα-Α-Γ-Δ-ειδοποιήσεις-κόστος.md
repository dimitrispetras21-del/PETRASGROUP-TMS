```
   ή   03:06 pg_cron ──► pg_net POST Worker /monitor/investigate ──► xAI API ──► UPDATE incidents.diagnosis [Γ, εναλλακτική]
```

- **Μπορεί το Grok Bot να ξυπνήσει μόνο του;** **ΝΑΙ για χρονοπρογραμματισμό, ΟΧΙ για webhook/API.** Τεκμηρίωση xAI (`docs.x.ai/grok-bot/skills-routines-and-automations`, 22/9): οι routines τρέχουν «*on a schedule or, where supported, after an event*»· «*A Bot can own up to 50 routines, and the app keeps the 20 most recent run records for each routine*»· «*Closing the app, your laptop, or your phone doesn't stop a background turn or a routine*» (`docs.x.ai/grok-bot/overview`). Event-triggers: η σελίδα γράφει «*Cursor account integrations can start a routine from an event, such as a Slack message or a GitHub notification*» — αφορά ενσωμάτωση Cursor, **όχι** Supabase/Postgres· για τη δική μας βάση **ΔΕΝ ΤΕΚΜΗΡΙΩΝΕΤΑΙ** event trigger. Webhook, HTTP trigger, CLI, API εκκίνησης routine: **ΔΕΝ ΤΕΚΜΗΡΙΩΝΟΝΤΑΙ** πουθενά στα docs. Έξοδος routine: «*post … in this conversation*» — αποστολή σε email/push/τηλέφωνο **ΔΕΝ ΤΕΚΜΗΡΙΩΝΕΤΑΙ**.
- Οι «Automations» του grok.com (`x.ai/news/grok-automations`, 16/7/2026: «*Scheduled automations are available to everyone; email triggers are included with SuperGrok*», παράδοση «*email, app notification, both, or neither*») είναι **άλλο προϊόν** (grok.com + iOS/Android), χωρίς connectors βάσης — δεν λύνει το Γ.
- **Συνέπεια σχεδίασης:** το Grok **δεν** είναι ο μηχανισμός αφύπνισης. Ξυπνά η **βάση** (pg_cron), ειδοποιεί η **βάση** (pg_net → Telegram), και το Grok **διαβάζει μια ουρά** σε προγραμματισμένη ώρα. Αν το Grok δεν τρέξει, η ειδοποίηση έχει ήδη φύγει (Στ4).

## Α. Καταγραφή με συσχέτιση — «κλικ → αίτημα → γραμμή βάσης» (ΠΡΟΣΧΕΔΙΟ, θέλει Worker deploy + bump front + migration)

### Α1. Τι υπάρχει σήμερα (ΓΕΓΟΝΟΣ)
- Κανένα αναγνωριστικό αιτήματος. `_apiHeaders(method)` (`core/api.js:357-370`) στέλνει μόνο `Authorization` + `Content-Type`· 11 σημεία κλήσης.
- `_atRetry` (`api.js:243-346`) ξαναστέλνει έως 3 φορές σε 5xx/δικτυακό σφάλμα → **ένα κλικ = έως 3 γραμμές** στον Worker, σήμερα αδιάκριτες.
- Ουρά offline: `_offlineQueue` σε `localStorage['tms_offline_queue']` (`api.js:95-160`), όχι στον SW (`sw.js:104` αφήνει τα non-GET να περάσουν). Στο flush ελέγχει `Last Modified` για σύγκρουση· τα αποτελέσματα (synced/conflict/failed) ζουν μόνο σε toast.
- Worker: `audit()` γράφει `actor, role, action, table_name, record_id, before_data, after_data, created_at` (`index.js:611-626`)· 27 κλήσεις `audit(env, …)` + 5 `auditMany(env, …)`. `/app-errors` δέχεται `message, stack, page, user_agent, sw_version` (`index.js:371-400`)· ο front στέλνει `page = location.href` (`utils.js:592-603`) — **περιέχει το hash της σελίδας, όχι query**.
- Από 22/9 21:08 τα αυτόματα invocation logs είναι **κλειστά** (`wrangler.toml` `invocation_logs = false`)· άρα σήμερα **δεν υπάρχει καμία γραμμή ανά αίτημα** πουθενά. Το Α χτίζει την επιλογή (ii) του `08`.

### Α2. Ελάχιστη σχεδίαση
**Front (`core/api.js`)** — ένα id **ανά ενέργεια χρήστη**, όχι ανά fetch:
```js
// api.js — ΠΡΟΣΧΕΔΙΟ. Ένα id ανά κλήση atPatch/atCreate/atDelete/atGet· τα retries κρατούν το ίδιο id, αλλάζει μόνο το -n.
function _newReqId() { return (crypto.randomUUID ? crypto.randomUUID() : String(Date.now()) + Math.random()).replace(/-/g,'').slice(0,26); }
function _apiHeaders(method, reqId, attempt) {          // reqId/attempt: προαιρετικά, ώστε τα 11 σημεία να αλλάξουν σταδιακά
  const h = { /* ό,τι σήμερα */ };
  if (reqId) h['x-tms-req'] = reqId + '-' + (attempt || 1); // ΠΟΤΕ το JWT, ΠΟΤΕ username
  return h;
}
```
- `_atRetry` περνά `attempt = i+1`. Σε αποτυχία, το Error αποκτά `e._req = reqId` και το `logError → _postAppError` στέλνει `req: entry.req` στο body του `/app-errors` (`utils.js:595-603`). Έτσι το σφάλμα browser και το αίτημα Worker έχουν **το ίδιο κλειδί** χωρίς να μεταφέρεται τίποτα άλλο.
- Ουρά offline: κάθε item κρατά `req` (το αρχικό) και στο flush στέλνει `x-tms-req: <req>-q` (q = replay). Στο τέλος του flush, **μία** κλήση `logError(new Error('offline flush'), 'queue', {synced, conflicts, failed, reqs:[…]})` με `severity:'info'` → `/app-errors` — ώστε το «αποθηκεύτηκε τοπικά» να αφήνει ίχνος κεντρικά (σήμερα δεν αφήνει: αρχή 1).
- `sw_version`: ο SW ήδη στέλνει `SW_ACTIVATED {version}` (`sw.js:85`, `app.html:246`) → αποθήκευση σε `window.__tmsSwVersion` και αποστολή στο `/app-errors` (κλείνει το Υ5 του `03`).

**Worker (`index.js:4737`)** — μία γραμμή JSON ανά αίτημα, **μετά** την απάντηση, τίποτα στο μονοπάτι του χρήστη:
```js
async fetch(request, env, ctx) {
  const t0 = Date.now(), req = (request.headers.get('x-tms-req') || '').slice(0, 40) || null;
  let res, role = null;
  try { res = await handleFetch(request, env, ctx); }              // = το σημερινό σώμα, αμετάβλητο
  catch (e) { console.error(JSON.stringify(reqLine(request, req, 500, t0, null, String(e && e.message).slice(0,120)))); throw e; }
  if (request.method !== 'OPTIONS') console.log(JSON.stringify(reqLine(request, req, res.status, t0, res.headers.get('x-tms-role'))));
  res.headers.delete('x-tms-role');                                  // ο ρόλος μπαίνει από τους handlers μόνο για το log, δεν φεύγει στον browser
  return res;
}
// reqLine → {kind:"req", req, method, path: url.pathname (ΧΩΡΙΣ query), status, ms, role, table: TABLES[id]?.pg ή πρόθεμα /costs|/pallets, action: GET→read POST→create PATCH→update DELETE→delete, rec: facadeMatch[2] || null, err?}
```
- `audit()`/`auditMany()` αποκτούν `req_id: entry.reqId` και οι 32 κλήσεις περνούν `reqId: request.headers.get('x-tms-req')` — μηχανική αλλαγή, ελέγχεται με `grep -c 'reqId:' = 32` πριν το deploy (Μ-έλεγχος).
- `handleAppErrorPost` προσθέτει `req_id: clampStr(body.req, 40)`.
- Το `err` **μόνο** σε status ≥ 500 και **μόνο** `e.message` (όχι `details`/`hint` του PostgREST, που μπορεί να περιέχουν τιμές γραμμών).

### Α3. Πώς γίνεται joinable
```sql
-- «Τι έγινε όταν ο χρήστης είδε σφάλμα;» — από το σφάλμα προς τη βάση (SELECT, ρόλος ανάγνωσης)
SELECT e.created_at, e.message, a.action, a.table_name, a.record_id, a.role
FROM app_errors e LEFT JOIN audit_log a ON a.req_id = e.req_id
WHERE e.req_id = '<req>' LIMIT 20;
-- Αντίστροφα: audit_log γραμμή → app_errors με ίδιο req_id → ο χρήστης είδε σφάλμα ΠΑΡΟΤΙ γράφτηκε (διπλή αποθήκευση, retry).
```
Το τρίτο σκέλος (γραμμή Worker) ζει στα Workers Logs (`kind:"req"`, πεδίο `req`) — ερώτηση από τον owner στο dashboard· **όχι από bot πριν τις 29/9** (`08`). Οι έλεγχοι Α4/Α5/Β4/Β5 του `02` ξαναγράφονται πάνω στο `kind:"req"` (status/method/path) — από τον ερευνητή του Β.

**Ειδικά σενάρια που γίνονται ορατά μόνο με το Α:** διπλό κλικ = δύο διαφορετικά `req` στο ίδιο δευτερόλεπτο, ίδιος `record_id` · retry = ίδιο `req`, `-1/-2/-3` · αποθήκευση που «πέτυχε» χωρίς `audit_log` = γραμμή `status 200` με `action:update` και **καμία** `audit_log` με αυτό το `req_id` (= σιωπηλή απόρριψη, μηχανισμός #1 — σήμερα το πιάνει μόνο έμμεσα το `facade_unknown_fields`).

## Γ. Πρωτόκολλο διερεύνησης Grok (μόνο ανάγνωση, χωρίς διόρθωση)

### Γ1. Πότε ξεκινά
Μόνο για γραμμή `monitoring.incidents` με `state='new'` ή `'recurred'` (από Β/Α) ή για **ανωμαλία** (Β2 σιωπή `app_errors` με κίνηση, Η2 σφάλματα ×2 μετά από deploy, Ζ7/Ζ11 αύξηση > 20%). Ποτέ για `known`, ποτέ δεύτερη φορά για το ίδιο `incident_key` την ίδια ημέρα. Ανώτατο: **5 πακέτα/ημέρα** (Στ5)· το 6ο μένει `diagnosis = 'ΕΚΚΡΕΜΕΙ — όριο ημέρας'`.

### Γ2. Πακέτο περιστατικού (φτιάχνεται από SQL, `monitoring.build_package(incident_id) → jsonb`, ≤ 4 KB)

### Γ3. Τι ζητείται από το Grok (system prompt = starter `01` + αυτό)
Ταξινόμηση **υποχρεωτικά σε μία** από 4 κατηγορίες, με τη λέξη πρώτη στην απάντηση:
1. **ΤΕΧΝΙΚΟ ΕΛΑΤΤΩΜΑ** — κώδικας/trigger/χάρτης έκανε ή δεν έκανε κάτι (ΓΕΓΟΝΟΣ μόνο αν το δείχνει `αρχείο:γραμμή@SHA` + εγγραφή).
2. **ΛΕΙΤΟΥΡΓΙΚΗ ΕΚΚΡΕΜΟΤΗΤΑ** — κάποιος δεν καταχώρισε ακόμη (= ΕΛΛΙΠΗΣ ΚΑΤΑΧΩΡΙΣΗ του `02`).
3. **ΑΠΟΔΕΚΤΗ ΕΞΑΙΡΕΣΗ** — ταιριάζει σε κλειδωμένη απόφαση ή ΙΣΤΟΡΙΚΟ· ο έλεγχος πρέπει να ενημερωθεί (πρόταση, όχι αλλαγή).
4. **ΕΛΛΙΠΗ ΣΤΟΙΧΕΙΑ** — τι ακριβώς SELECT/άνοιγμα οθόνης θα το έκρινε.

Πρότυπο εξόδου (ελληνικά, ≤ 1 οθόνη, **καμία διόρθωση, κανένα SQL εγγραφής, κανένα patch**):
```
ΔΙΑΓΝΩΣΗ <incident_key> — <ώρα εργαλείου>
ΚΑΤΗΓΟΡΙΑ: ΤΕΧΝΙΚΟ ΕΛΑΤΤΩΜΑ | ΛΕΙΤΟΥΡΓΙΚΗ ΕΚΚΡΕΜΟΤΗΤΑ | ΑΠΟΔΕΚΤΗ ΕΞΑΙΡΕΣΗ | ΕΛΛΙΠΗ ΣΤΟΙΧΕΙΑ
ΕΠΙΧΕΙΡΗΣΙΑΚΗ ΕΠΙΠΤΩΣΗ: <ρόλος, οθόνη, τι δεν θα γίνει σήμερα — μία πρόταση>
ΓΕΓΟΝΟΤΑ: <μόνο ό,τι είναι μέσα στο πακέτο, με αναφορά πεδίου>
ΥΠΟΘΕΣΗ: <μία, με το τι θα την επιβεβαίωνε>
ΕΠΟΜΕΝΟ ΒΗΜΑ (ποιος): <owner | dispatcher | accountant | συντονιστής> — <ένα ασφαλές βήμα ανάγνωσης ή μία απόφαση>
ΔΕΝ ΒΛΕΠΩ: <τι λείπει από το πακέτο>
```
Η κατάσταση του ελέγχου **δεν αλλάζει** από τη διάγνωση (κόκκινο μένει κόκκινο). Το `state` του incident το αλλάζει μόνο άνθρωπος (Στ5).

### Γ4. Πώς φτάνει το πακέτο στο Grok — δύο δρόμοι
| | Γ-Bot (routine) | Γ-API (Worker → xAI) |
|---|---|---|
| Εκκίνηση | Προγραμματισμένη routine 06:30 στο Grok Bot (τεκμηριωμένη) · SELECT `monitoring.incidents WHERE state IN ('new','recurred') AND diagnosis IS NULL` μέσω Supabase connector | `pg_cron` 03:06 → `net.http_post(<worker>/monitor/investigate, headers {x-monitor-key})` → ο Worker καλεί `api.x.ai` με `XAI_API_KEY` (secret CF, όπως σήμερα το `ANTHROPIC_API_KEY` στο `handleAiMessages`, `index.js:742`) → `UPDATE monitoring.incidents SET diagnosis, diagnosed_at, model, tokens` |
| Πού πάει η διάγνωση | Στη συνομιλία του Bot (ο owner τη διαβάζει στην εφαρμογή)· write-back **αδύνατο** (SELECT-only) | Στη βάση → η πρωινή ειδοποίηση 07:00 τη συμπεριλαμβάνει |
| Κόστος | 0 € επιπλέον (συνδρομή)· όρια χρήσης routine **ΑΓΝΩΣΤΑ** | ~2–3 $/μήνα (Στ5) |
| Ρίσκο | Το connector Supabase μένει με τον ρόλο `tms_monitor` (όχι service_role) | Deploy Worker (φρουρός), νέο secret, όριο κλήσεων στον Worker |
| Πρόταση | **Πιλότος** (εβδομάδες 1–3) | Όταν χρειαστεί η διάγνωση στο τηλέφωνο χωρίς να ανοίξει η εφαρμογή |

| Τι μπορεί να πεθάνει | Πώς φαίνεται | Μηχανισμός |
|---|---|---|
| Το `pg_cron` δεν έτρεξε / η function σκάει | Καμία γραμμή `health_checks` με `run_at::date = today` | **Dead-man εκτός Supabase:** healthchecks.io (free «Hobbyist»: 20 checks, 100 log entries/check — `healthchecks.io/pricing`, 22/9). ### Στ5.3 Περιστατικά: κλειδί, καταστάσεις, καταστολή
- `incident_key = check_id || ':' || coalesce(entity_table,'') || ':' || coalesce(entity_id,'')` (όπως `skill` §4: `Β3:ramp:Truck`). Ίδιο κλειδί = ίδιο περιστατικό.
- Καταστάσεις: `new` → (`confirmed` | `false_alarm`) → `resolved` → `recurred` (αν ξαναβγεί κόκκινο **μετά** από `resolved`, νέα ειδοποίηση). Μόνο άνθρωπος περνά σε `confirmed/false_alarm/resolved` (UPDATE από owner/συντονιστή)· `resolved` **μόνο** αν ο έλεγχος ξαναέτρεξε πράσινο (`resolved_verified_at`).
- Καταστολή: **1 ειδοποίηση/κλειδί/24 ώρες** εκτός `worsened` (τιμή ×2 ή +50 %)· `false_alarm` σιωπά 30 ημέρες (μετά ξανά `new`, ώστε η εξαίρεση να μπει **στον έλεγχο**, όχι στη λίστα).

```sql
-- 045_monitoring_incidents.sql — ΠΡΟΣΧΕΔΙΟ (schema monitoring: από τον ερευνητή του Β· εδώ μόνο ο πίνακας περιστατικών)
CREATE TABLE monitoring.incidents (
  id bigserial PRIMARY KEY, incident_key text NOT NULL, check_id text NOT NULL,
  entity_table text, entity_id text, severity text NOT NULL CHECK (severity IN ('P1','P2','P3','P4','MECH')),
  state text NOT NULL DEFAULT 'new' CHECK (state IN ('new','confirmed','false_alarm','resolved','recurred')),
  value numeric, expected text, first_seen timestamptz NOT NULL DEFAULT now(), last_seen timestamptz NOT NULL DEFAULT now(),
  occurrences int NOT NULL DEFAULT 1, package jsonb, diagnosis text, diagnosed_at timestamptz, model text, tokens_in int, tokens_out int,
  notified_at timestamptz, notify_channel text, human_note text, state_changed_by text, state_changed_at timestamptz, resolved_verified_at timestamptz
);
CREATE UNIQUE INDEX incidents_open_key ON monitoring.incidents (incident_key) WHERE state IN ('new','confirmed','recurred');
CREATE TABLE monitoring.limits (name text PRIMARY KEY, value numeric NOT NULL);  -- 'investigations_per_day'=5, 'tokens_per_month'=2000000, 'notifications_per_day'=20
-- tms_monitor: INSERT/UPDATE μόνο σε monitoring.incidents (diagnosis*, notified_at), ποτέ DELETE. Ο owner αλλάζει state με τον δικό του ρόλο.
```
