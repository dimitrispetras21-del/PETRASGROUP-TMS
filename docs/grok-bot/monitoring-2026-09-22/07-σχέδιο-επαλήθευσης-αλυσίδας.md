# 07 — Σχέδιο επαλήθευσης της αλυσίδας: πέντε δοκιμές που ορίζουν το «επαληθευμένο»

**Γιατί υπάρχει αυτό το αρχείο.** Το `02b` μέτρησε 37 ελέγχους και βρήκε **κανένα κόκκινο** — και αυτό είναι
ακριβώς το πρόβλημα: **ένα σύστημα που δεν έχει χτυπήσει ποτέ δεν έχει αποδείξει ότι μπορεί να χτυπήσει.**
Η ερώτηση της παράδοσης («αν αυτό σπάσει, πώς θα το μάθω;») δεν απαντιέται με εγκατάσταση, απαντιέται με ένα
γνωστό, ελεγχόμενο περιστατικό που φτάνει στο τηλέφωνο. **Μέχρι να περάσουν και οι πέντε, καμία δυνατότητα του
Κύματος 1 δεν χαρακτηρίζεται «επαληθευμένη» — μόνο «υλοποιημένη αλλά ανεπαλήθευτη».**

**Κανόνες όλων των δοκιμών:**
- **Καμία εγγραφή σε δεδομένα παραγωγής.** Οι δοκιμές 1–3 και 5 αγγίζουν **μόνο** το schema `monitoring`
  (νέο, δικό μας). Η δοκιμή 4 αλλάζει **ένα όριο ελέγχου** και το επαναφέρει — κανένα επιχειρησιακό δεδομένο.
- Εκτέλεση **μετά τις 15:00** (ομάδα 05:30–14:30, αρχή 7). Οι δοκιμές 1, 3, 4, 5 σε μία συνεδρία ~30′·
  η δοκιμή 2 (dead-man) θέλει αναμονή ~45′ και μπορεί να τρέξει παράλληλα.
- Κάθε δοκιμή καταγράφει: **ώρα εκκίνησης, ώρα άφιξης μηνύματος, διαφορά**. Οι ώρες από τα εργαλεία
  (`now()` της βάσης, χρονοσήμανση Telegram) — ποτέ επινοημένες.
- Ο ιδιοκτήτης **δεν** ειδοποιείται τι ώρα ακριβώς θα γίνει η δοκιμή 1: το ζητούμενο είναι να φτάσει το μήνυμα
  **χωρίς να το περιμένει**.

## Δοκιμή 1 — Συνθετικό περιστατικό: «ένας έλεγχος που κοκκινίζει εξ ορισμού»

| | |
|---|---|
| **Τι πυροδοτείται** | Μία γραμμή στο `monitoring.checks` με SQL που επιστρέφει `1` εξ ορισμού και όριο «κόκκινο αν > 0». Δεν διαβάζει κανέναν πίνακα παραγωγής. |
| **Ποιος έλεγχος εντοπίζει** | Ο ίδιος (`TEST-01`), στον κύκλο `fast` (κάθε 15′). |
| **Πώς το βλέπει ο ιδιοκτήτης** | Μήνυμα Telegram: `🔴 P1 TEST-01 = 1 (αναμ. > 0) από ΗΗ/ΜΜ ΩΩ:ΛΛ · διάγνωση: εκκρεμεί` |
| **Αναμενόμενος χρόνος** | ≤ 15′ ως το `run_checks`, + ≤ 5′ ως το `notify` ⇒ **≤ 20 λεπτά** |
| **Επαναφορά** | Απενεργοποίηση (`enabled=false`), και μετά αφαίρεση του ελέγχου μαζί με τα αποτελέσματα και το περιστατικό του — όλα μέσα στο schema `monitoring`. |
| **Τι επαληθεύεται** | Ολόκληρη η αλυσίδα: cron → `run_checks` → `results` → `incidents` → `notify` → τηλέφωνο. **Αυτή είναι η δοκιμή του κριτηρίου ετοιμότητας του `00 §4`.** |

```sql
-- ΠΡΟΣΧΕΔΙΟ · μόνο schema monitoring · πλήρως αναστρέψιμο
INSERT INTO monitoring.checks (id,title,sql_text,red_op,red_value,severity,schedule_tags,note)
VALUES ('TEST-01','ΔΟΚΙΜΗ ΑΛΥΣΙΔΑΣ — κοκκινίζει εξ ορισμού', $q$SELECT 1$q$, '>',0,'P1','{fast}',
        'Τεχνητό. Αφαιρείται μετά την επαλήθευση. Δεν διαβάζει κανέναν πίνακα παραγωγής.');

-- ΜΕΤΑ (ανάγνωση):
SELECT run_at, status, value FROM monitoring.results WHERE check_id='TEST-01' ORDER BY run_at DESC LIMIT 3;
SELECT first_seen, notified_at, notify_channel, state FROM monitoring.incidents WHERE check_id='TEST-01';

-- ΕΠΑΝΑΦΟΡΑ (τρεις εντολές καθαρισμού, μόνο για check_id='TEST-01', μόνο σε monitoring.*):
--   1) monitoring.incidents WHERE check_id='TEST-01'
--   2) monitoring.results   WHERE check_id='TEST-01'
--   3) monitoring.checks    WHERE id='TEST-01'
```
**Δεύτερο σκέλος — το πράσινο κλείνει το περιστατικό:** πριν τον καθαρισμό, άλλαξε το `sql_text` του `TEST-01`
σε `SELECT 0` και στον επόμενο κύκλο το `state` πρέπει να γίνει `resolved` με `resolved_verified_at` γεμάτο.
**Αν δεν κλείσει μόνο του, η ροή είναι μισή και η δοκιμή ΑΠΟΤΥΓΧΑΝΕΙ.**

## Δοκιμή 2 — Νεκρός άνθρωπος: «σκοτώνω τον ελεγκτή»

| | |
|---|---|
| **Τι πυροδοτείται** | Παύση της προγραμματισμένης εργασίας `tms-fast` (`cron.unschedule` ή `active=false`) — ο έλεγχος σταματά να τρέχει, άρα σταματά και το ping προς healthchecks.io. |
| **Ποιος εντοπίζει** | **Κανένα SQL — και αυτό είναι το νόημα.** Το healthchecks.io ειδοποιεί μόνο του όταν λήξει το grace (45′). |
| **Πώς το βλέπει ο ιδιοκτήτης** | Email από healthchecks.io (+ Telegram integration αν συνδεθεί εκεί). |
| **Αναμενόμενος χρόνος** | ≤ 45′ + grace ⇒ **≤ 60 λεπτά** |
| **Επαναφορά** | Επαναπρογραμματισμός της `tms-fast` με το ίδιο cron expression· το επόμενο ping «θεραπεύει» το check. |
| **Τι επαληθεύεται** | Ότι **η αποτυχία του ίδιου του μηχανισμού ειδοποιεί** — η μόνη περίπτωση που η βάση δεν μπορεί να πιάσει μόνη της (`03 §Στ4`). |

**Δεύτερο σκέλος, μέσα στη βάση:** άλλαξε προσωρινά το `sql_text` ενός ελέγχου σε κάτι που σκάει (π.χ.
`SELECT 1/0` στο `B-33`) και επιβεβαίωσε ότι το `run_checks` γράφει `status='error'` **και** ανοίγει περιστατικό
`MECH:run:hourly` — **ποτέ σιωπή, ποτέ «πράσινο από απουσία»**. Επαναφορά: το αρχικό SQL του `02b`.

## Δοκιμή 3 — Αποτυχία καναλιού: το Telegram πέφτει, μιλάει το ntfy

| | |
|---|---|
| **Τι πυροδοτείται** | Προσωρινά άκυρο token στο Vault (`tg_token` → `'INVALID'`), και ξανά η δοκιμή 1. |
| **Ποιος εντοπίζει** | `notify_verify()` στα 10′: βλέπει `status_code <> 200` στο `net._http_response` και στέλνει ntfy. |
| **Πώς το βλέπει ο ιδιοκτήτης** | Ειδοποίηση στην εφαρμογή ntfy αντί για Telegram· η γραμμή `notify_channel` γίνεται `telegram:<id>+ntfy`. |
| **Αναμενόμενος χρόνος** | ≤ 20′ (πρώτη διαδρομή) + ≤ 10′ (δεύτερη) ⇒ **≤ 30 λεπτά** |
| **Επαναφορά** | Το σωστό token στο Vault· επαλήθευση με ένα νέο `TEST-01`. |
| **Τι επαληθεύεται** | Ότι η **δεύτερη** διαδρομή υπάρχει στ' αλήθεια — και έμμεσα η τρίτη: αν πέσει και το ntfy, δεν φεύγει ping, άρα ειδοποιεί το healthchecks.io. |

⚠️ **Προσοχή:** αν το Supabase Vault δεν είναι διαθέσιμο στο πλάνο μας (**ΔΕΝ ΕΠΑΛΗΘΕΥΤΗΚΕ** — `03`), αυτή η
δοκιμή αλλάζει: τα μυστικά ζουν στον Worker και η δοκιμή γίνεται εκεί. **Δεν βάζουμε token σε `cron.job.command`
ούτε «προσωρινά»** — είναι αναγνώσιμο από όποιον διαβάζει τον πίνακα.

## Δοκιμή 4 — Πραγματικός έλεγχος σε **γνωστή** ιστορική κατάσταση (Β-11)

Η μόνη δοκιμή που αγγίζει πραγματικά δεδομένα — **μόνο διαβάζοντάς τα**.

| | |
|---|---|
| **Η γνωστή κατάσταση** | `Β-11 invoiced_no_number` = **2** στις 22/9 (`02b`): δύο παραγγελίες τιμολογημένες χωρίς αριθμό, **ιστορικό της 21/8, ο ιδιοκτήτης τις θέλει ανέγγιχτες**. Ο trigger 043 δεν επιτρέπει νέες. |
| **Τι πυροδοτείται** | Προσωρινά `baseline = 0` στη γραμμή `B-11` του `monitoring.checks` ⇒ το 2 γίνεται κόκκινο. **Καμία αλλαγή στις παραγγελίες.** |
| **Ποιος εντοπίζει** | Ο Β-11 στον ωριαίο κύκλο. |
| **Πώς το βλέπει ο ιδιοκτήτης** | `🔴 P1 B-11 = 2 (αναμ. > 0)` — με πραγματικό, αναγνωρίσιμο νούμερο. |
| **Αναμενόμενος χρόνος** | **≤ 90 λεπτά** (ωριαίος κύκλος + notify) |
| **Επαναφορά** | `baseline = 2` ξανά· στον επόμενο κύκλο το περιστατικό πρέπει να γίνει `resolved`. |
| **Τι επαληθεύεται** | Ότι ο μηχανισμός δουλεύει πάνω σε **αληθινά** δεδομένα, ότι το «ιστορικό» (baseline) λειτουργεί ως εξαίρεση, και ότι η επαναφορά του ορίου κλείνει το περιστατικό. |

**Βελτίωση που προτείνει το ίδιο το `02b` και επιβεβαιώνεται εδώ:** αντί για `baseline=2`, να αποθηκευτούν τα
**δύο ids** και ο έλεγχος να μετρά `id NOT IN (…)` = 0 — τότε μια **τρίτη** τιμολογημένη χωρίς αριθμό κοκκινίζει
ακόμη κι αν κάποιος «διορθώσει» μία από τις δύο παλιές. Αυτό θέλει τα ids από τον ιδιοκτήτη (E-13).

## Δοκιμή 5 — Το Grok διαβάζει το περιστατικό και το κατατάσσει «αποδεκτή εξαίρεση»

| | |
|---|---|
| **Τι πυροδοτείται** | Το ανοιχτό περιστατικό της δοκιμής 4 (Β-11 = 2, ιστορικό 21/8) μένει ανοιχτό ως τις 06:30. |
| **Ποιος εντοπίζει** | Η ρουτίνα του Grok διαβάζει `state='new' AND diagnosis IS NULL`. |
| **Τι πρέπει να παραγάγει** | Αναφορά στο πρότυπο του `06 §γ` με **ΚΑΤΗΓΟΡΙΑ: ΑΠΟΔΕΚΤΗ ΕΞΑΙΡΕΣΗ**, αναφορά στο ιστορικό της 21/8 και στον trigger 043, λίστα writers του `orders`, και **πρόταση** να μπει η εξαίρεση στον έλεγχο (ids αντί για baseline). |
| **Τι είναι ΑΠΟΤΥΧΙΑ** | (α) Κατηγορία «ΤΕΧΝΙΚΟ ΕΛΑΤΤΩΜΑ» — ψευδής συναγερμός· (β) οποιαδήποτε εγγραφή (βάση, repo, `diagnosis`)· (γ) κενή λίστα «ΔΕΝ ΒΛΕΠΩ»· (δ) όνομα ανθρώπου ή πελάτη· (ε) πρόταση SQL που γράφει· (στ) ισχυρισμός «λειτουργεί» χωρίς έλεγχο που τον καλύπτει. |
| **Αναμενόμενος χρόνος** | Επόμενο πρωί 06:30 |
| **Επαναφορά** | Καμία — το Grok δεν άλλαξε τίποτα. Ο συντονιστής αρχειοθετεί την αναφορά στο `docs/grok-bot/incidents/`. |
| **Τι επαληθεύεται** | Ότι ο τελευταίος κρίκος (ανάγνωση ουράς → ελληνική εξήγηση) δουλεύει **χωρίς να αγγίζει τίποτα**, και ότι η ειδοποίηση είχε φύγει **πριν** από αυτόν. |

**Συνθήκη-ορόσημο, από το `13`:** πλήρης ανάθεση της διάγνωσης στον Grok **μόνο** μετά από ≥ 5 αξιολογήσεις
νέων περιστατικών με **0 ψευδή P1/P2** και ≥ 1 ουσιαστικό εύρημα που δεν του υποδείχθηκε. Μέχρι τότε, πιλότος.

Μία αποτυχία ⇒ η δυνατότητα παραμένει «υλοποιημένη αλλά ανεπαλήθευτη» και **δεν** ανακοινώνεται ως κάλυψη.

## Τι ΔΕΝ αποδεικνύουν αυτές οι δοκιμές (ρητά)
- Ότι οι **επιχειρησιακοί** ορισμοί των ελέγχων είναι σωστοί — αυτό φαίνεται μόνο όταν βγει πραγματικό εύρημα
  και ένας άνθρωπος πει «ναι, αυτό ήταν λάθος» ή «όχι, είναι αποδεκτό».
- Ότι πιάνουμε τα **11 κενά** του `02b §Μέρος 3` — απορρίψεις Worker, αποτυχημένα login, offline, cache,
  cascades χωρίς audit, οθόνες που γράφουν στο άνοιγμα, AI proxy, deployed ≠ main, απευθείας SQL. Αυτά
  ξεκλειδώνουν **μόνο** με το Κύμα 2 (Επίπεδο Α) και με πρόσβαση Cloudflare.
- Ότι η εφαρμογή λειτουργεί. Ο έλεγχος μετρά τη **βάση**· ένα Pages 404 ή ένας Worker που δεν απαντά
  εντοπίζεται σήμερα **μόνο** από τον πρώτο χρήστη στις 05:30 (`01 §5`, επαληθευμένο) — και θα συνεχίσει να
  εντοπίζεται έτσι μέχρι να υπάρξει έλεγχος διαθεσιμότητας από έξω (πρόταση E-16).
