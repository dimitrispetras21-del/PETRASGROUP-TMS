### 3.4 Χιλιόμετρα — κρυμμένα μέσα στο κείμενο

**74 γραμμές** έχουν την ένδειξη χιλιομέτρων μέσα στην περιγραφή, σε ασυνεπή μορφή:

```

"…SILENCER,OIL,ENGINEOIL , ΧΛΜ 74198"      → τέλος γραμμής
```

Εξάγονται με regex `(?:ΧΛΜ|KM)\s*[:.]?\s*(\d{4,7})|(\d{4,7})\s*(?:ΧΛΜ|KM)` — **αλλά
χρειάζεται έλεγχο εύλογου ορίου** (π.χ. 50.000–2.500.000) γιατί το ίδιο μοτίβο πιάνει
και ποσότητες («6 ΕΛΑΣΤΙΚΑ»). Προτείνεται αυτόματη εξαγωγή **με σημαία `needs_review`**,

### 4.1 Το πρόβλημα του `Type`

Το `Type` είναι single-select `Service / Repair / Inspection / Tyre` — η πηγή δεν έχει
αντίστοιχη στήλη. Δοκιμή αυτόματης ταξινόμησης με λέξεις-κλειδιά στην περιγραφή +
προμηθευτή:

| Type | Γραμμές | Κανόνας |
|---|---|---|
| `Service` | 299 | `ΣΕΡΒΙΣ\|SERVICE\|ΦΙΛΤΡ\|ΛΑΔΙ` |
| `Tyre` | 164 | `ΕΛΑΣΤΙΚ\|ΖΑΝΤ\|ΕΥΘΥΓΡΑΜΜ` + προμηθευτής `ΤΣΕΡΚΕΖΟΣ` |
| `Inspection` | 17 | `ΚΤΕΟ\|ΤΑΧΟΓΡΑΦ\|ΕΛΕΓΧΟΣ` |
| `Repair` (fallback) | **1.223** | ό,τι απομένει |

**Το 72% καταλήγει σε `Repair` ως καταφύγιο** — δηλαδή το πεδίο δεν θα φέρει
πληροφορία. Δύο επιλογές, θέλει απόφαση owner:

- **(α)** Αποδοχή: `Repair` = «ό,τι δεν είναι σέρβις/λάστιχα/έλεγχος». Ειλικρινές, φιλτράρει
  χρήσιμα το `Service` και το `Tyre` (τα δύο που ενδιαφέρουν για κόστος ανά χλμ).
- **(β)** Ταξινόμηση στο επίπεδο **συμβάντος** μετά την ομαδοποίηση (§5.1) — μια ομάδα
  «ΑΝΤΑΛΛΑΚΤΙΚΑ + ΕΡΓΑΣΙΑ» παίρνει τον τύπο της πιο περιγραφικής γραμμής της. Ανεβάζει
  αισθητά την ακρίβεια χωρίς χειρωνακτική δουλειά.

Προτείνεται **(β)**, με τη σαφή σημείωση ότι το `Type` είναι **παράγωγο, όχι
καταγεγραμμένο** — και άρα δεν πρέπει να χρησιμοποιηθεί ως ελεγκτικό στοιχείο.

## 5. Πρόταση κανονικοποιημένου μοντέλου

### 5.1 Απόφαση κοκκομετρίας — **1 εγγραφή ανά συμβάν** (όχι ανά γραμμή Excel)

Οι δύο επιλογές:

| | Α. 1:1 (1.703 εγγραφές) | Β. Ομαδοποιημένο (1.152 εγγραφές) |
|---|---|---|
| Πιστότητα στην πηγή | πλήρης | το άθροισμα διατηρείται |
| «ΕΡΓΑΣΙΑ» χωρίς συμφραζόμενα | 503 άχρηστες εγγραφές | ενσωματώνονται |
| `Cost` ανά συμβάν | θέλει άθροιση στο UI | άμεσο |
| `Parts` | κενό | ✅ γεμίζει από τη γραμμή ανταλλακτικών |
| Αναστρεψιμότητα | — | με `Notes` (§5.4) |

➡️ **Πρόταση: Β.** Κλειδί ομαδοποίησης `(πινακίδα, ημερομηνία, προμηθευτής)` — παράγει
1.152 συμβάντα, μέγιστο 4 γραμμές ανά συμβάν. Ανά συμβάν:

- `Cost` = άθροισμα καθαρών αξιών των γραμμών
- `Description` = συνένωση των μη γενικόλογων περιγραφών
- `Parts` = το κείμενο της γραμμής που ταυτοποιείται ως ανταλλακτικά
- `Type` = από την πιο περιγραφική γραμμή

Η επιλογή Β **δεν χάνει τίποτα** εφόσον κρατηθεί το ίχνος (§5.4) — και μόνο έτσι
αποκτούν νόημα τα 503 σκέτα «ΕΡΓΑΣΙΑ».

### 5.2 `WORKSHOPS` — προϋπόθεση, όχι επιλογή

Το `Workshop` στο `MAINT_HISTORY` είναι **linked record** — το UI ήδη γράφει
`fields['Workshop'] = [id]`. Άρα ο πίνακας πρέπει να **προϋπάρχει και να είναι
πλήρης** πριν την πρώτη εγγραφή, αλλιώς 1.703 γραμμές μένουν με κενό συνεργείο.

```
WORKSHOPS
  id
  name            ← κανονικό όνομα (εγκεκριμένο από owner)
  aliases[]       ← οι 107 raw παραλλαγές, για μελλοντικό import
  country         ← GR / BG  (η τιμή 'ΒΟΥΛΓΑΡΙΑ' δείχνει ότι χρειάζεται)
  active
```

Το `aliases[]` είναι το σημαντικό: κάνει το επόμενο import (2027) αυτόματο.

### 5.3 Ο preventive tracker **δεν πάει** στο `MAINT_HISTORY`

Είναι κατάσταση, όχι συμβάν: αντικαθίσταται, δεν συσσωρεύεται. Αν μπει ως 35 εγγραφές
ιστορικού, θα διπλομετρηθεί με τις καρτέλες και θα «παγώσει» ένα snapshot ως γεγονός.

Επιπλέον, η διασταύρωση δείχνει ότι **δεν συμφωνεί** με τις καρτέλες: από τα 29
οχήματα με ημερομηνία τελευταίου σέρβις, **μόνο 18 (62%)** έχουν αντίστοιχη γραμμή στην
καρτέλα την ίδια ημέρα. Λείπουν 11, μεταξύ τους `CB0229PB` (24-6-2026), `CB5284TP`
(17-7-2026), `IAZ7244` (22-6-2026). Δηλαδή **τα δύο αρχεία δεν συντηρούνται μαζί**.

➡️ **Πρόταση: ξεχωριστός πίνακας κατάστασης** — μία γραμμή ανά όχημα, ενημερώνεται:

```
MAINT_PLAN                        (1 εγγραφή ανά όχημα)
  vehicle_plate      → TRUCKS / TRAILERS
  vehicle_type       Truck | Trailer
  service_interval_km          60000 | 75000 | 90000   ← σταθερό ανά μοντέλο
  last_service_date
  last_service_odometer_km
  next_service_km              (παράγωγο: last_odo + interval)
  current_odometer_km
  odometer_reading_date        ← 2026-07-31 στην πρώτη φόρτωση
```

Το `next_service_km` σήμερα είναι **αποθηκευμένο** στο Excel αλλά είναι παράγωγο —
προτείνεται να υπολογίζεται, ώστε να μη ξεσυγχρονίζεται. Η στήλη «υπόλοιπο» (G) το ίδιο.

Δύο οχήματα βγαίνουν **ήδη ληξιπρόθεσμα**: `HMM6272` (−816.870) και `EKA7481` (−197.630)
— και τα δύο με `active=null` στη βάση, άρα πιθανότατα εκτός στόλου (θόρυβος, όχι alert).

Λείπουν 5 πεδία από τον tracker: `CB8214OB` και `IAB4166` χωρίς ημερομηνία τελευταίου
σέρβις (και τα δύο **ενεργά** — πραγματικό κενό, όχι θόρυβος).

**Τα ρυμουλκούμενα δεν καλύπτονται καθόλου** από preventive tracking σήμερα.

### 5.4 Ίχνος προέλευσης

Ώστε το migration να είναι ελέγξιμο και αναστρέψιμο, προτείνεται κάθε εγγραφή να φέρει
στο `Notes` δομημένο πρόθεμα (ίδια σύμβαση με τα notes του fleet import):

```
SRC: ΚΑΡΤΕΛΑ ΣΥΝΤΗΡΗΣΗΣ ΟΧΗΜΑΤΑ.xlsx / φύλλο 'ΙΑΒ 2103' / γρ. 12,13
RAW_SUPPLIER: ΓΕΩΡΓΙΑΔΗΣ(ΣΟΥΛΗΣ )
GROSS_XLSX: 1187.68
FLAGS: odometer_inferred
```

Χωρίς αυτό, κάθε μελλοντική διαφωνία «γιατί λέει 1.152 και όχι 1.703» είναι ανεπίλυτη.

### 5.5 Συνολικό σχήμα

```
TRUCKS ─┐
        ├──< MAINT_HISTORY >── WORKSHOPS
TRAILERS┘         (1.152)         (~45)
        │
        └──< MAINT_PLAN
              (35 → 85 όταν μπουν και τα ρυμουλκούμενα)
```

`MAINT_HISTORY` = συμβάντα (append-only) · `MAINT_PLAN` = κατάσταση (update-in-place).
Η σύνδεση με τα οχήματα μένει **κειμενική πινακίδα** όπως σήμερα — αλλά ο κανόνας του
`HANDOFF.md` ισχύει απαρέγκλιτα: *αλλαγή πινακίδας σε TRUCKS/TRAILERS πρέπει να γίνεται
ταυτόχρονα και στο `MAINT_HISTORY`*. Με 1.152 εγγραφές αυτό γίνεται πραγματικός κίνδυνος
— **προτείνεται foreign key σε `vehicle_id`** αντί για κείμενο, με την πινακίδα ως
denormalized στήλη μόνο για εμφάνιση.
